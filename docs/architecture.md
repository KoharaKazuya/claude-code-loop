# アーキテクチャ

コードを読めば分かる事実の羅列は避け、「なぜこの形になっているか」だけをまとめる。

## ツール本体をリポジトリの外に置く

ccloop は DevContainer feature としてインストールされ、`/usr/local/share/ccloop/` に本体が置かれる。
利用側リポジトリに残るのは `.agent/` 配下の設定・記録だけである。

- ツール本体のアップデートが利用側リポジトリの diff にならない。feature のバージョンを上げてコンテナを
  再ビルドするだけで全リポジトリに反映できる。
- 複数リポジトリに同じ仕組みを持ち込むとき、コピーしたコードが各リポジトリで少しずつ乖離していく問題が
  起きない。
- 利用側は「何を自律実行に任せるか(GOAL.md)」と「実行結果の記録(tasks/decisions/human-review)」
  だけを持てばよく、実行エンジンの実装詳細を気にしなくてよい。

この設計の裏返しとして、ツールは「利用側リポジトリのどこにインストールされたか」を前提にできない
(`lib/paths.ts` のコメント参照)。リポジトリルートは `--repo` / `CCLOOP_REPO` / cwd からの `.git` 探索で
実行時に決定する。

## この開発用 devcontainer は checkout の `bin/ccloop` を直接使う理由

`.devcontainer/post-create.sh` が `/usr/local/bin/ccloop` をこのリポジトリの `bin/ccloop`
(`lib/cli.ts` を Node の type-stripping でそのまま実行するランチャー)への symlink として作る。

- `lib/` を編集すれば、新しく起動するプロセスから即座にその変更が反映される。release してコンテナを
  再ビルドする往復を待たずに検証できる。
- エンドユーザー向けのインストール経路(公開済み feature / `install.sh`)自体の検証はこの devcontainer
  では行わず、CI の `feature-test` ジョブ(`devcontainer features test` を実行)が担う。エンドユーザーの
  インストール方法(公開済み feature の追加)は変わらない。

注意点として、自律ループ(`ccloop run`)自身がこのリポジトリの `lib/` を壊す変更を入れると、同じ
symlink を通じて PATH 上の `ccloop` コマンド自身も壊れる(自己改変からの隔離は無い)。壊れた場合は
`git` でその変更を戻せば復旧する。

## インストール済み ccloop とリポジトリ `lib/` の乖離検出

`ccloop status` は、自己ホスト(`package.json` の `name` が `claude-code-loop` であるリポジトリ)を
操作しており、かつインストール先がそのリポジトリの `lib/` とは別の実体を指す場合に限り、両者のソース
ハッシュを比較し、乖離していれば警告を 1 行表示する(`lib/supervisor.ts` の
`isInstalledSourceDrifted` / `installedSourceDriftLines`)。

この開発用 devcontainer では PATH 上の `ccloop` がリポジトリの `lib/` そのものを指すため、判定上
「乖離しない」側になり、この警告は出ない。公開済み feature や `install.sh` で別途インストールした
ccloop を使ってこのリポジトリを devcontainer の外から操作する場合は、インストール先がリポジトリの
`lib/` と食い違いうるため、この警告が点灯しうる。

## `.claude/` を要求しない

利用側リポジトリに `.claude/CLAUDE.md` や `.claude/agents/reviewer.md` を置く運用も可能だが、ccloop は
それを要求しない。共通ルールは `claude -p` 起動時に `--append-system-prompt-file` で、reviewer
サブエージェントは `--agents` で、permissions/hooks は生成した `--settings` で注入する。

理由は、`.claude/` を持ち込むと利用側リポジトリの他の Claude Code の使い方(人間の対話セッションなど)
と設定が衝突しうるため、ccloop の関心事(自律実行セッションの挙動)を利用側の `.claude/` 設定から
完全に切り離したいから。利用側リポジトリに元から `CLAUDE.md` があれば、それは通常どおり Claude Code が
読み込むので共存できる。

**既知の制約**: `--append-system-prompt-file` で注入した内容は、fork でないサブエージェント
(Task ツールで起動されたセッション)には引き継がれない。そのため自律実行セッションが他のサブエージェント
へ委譲するときは、守らせたいルール(AskUserQuestion を使わない、permissions.deny に一致する操作をしない、等)を
委譲プロンプト本文に定型文として明示的に書く必要がある(`lib/prompt/PROMPT.md` の「委譲時の定型注意」)。
これは仕組み上の制約であり、将来 Claude Code 側の挙動が変わらない限り解消されない。

## 実行時状態を `~/.local/state` に置く

`state.json` / `metrics.jsonl` / `permission-denials.jsonl` / `runner.json` / `patches/` / 生成された
settings・system prompt / `worktrees/` は、利用側リポジトリの外、XDG state ディレクトリ
(`${XDG_STATE_HOME:-~/.local/state}/ccloop/<リポジトリ名>-<ハッシュ>/`)に置く。

- git 管理外にしたい実行時ファイルを `.gitignore` で除外し続ける手間・漏れのリスクを無くせる。
- 利用側リポジトリの親ディレクトリへの書き込み権限が要らない(devcontainer の `/workspaces` は root
  所有で、兄弟ディレクトリを作るには sudo が要る環境がある)。
- タスクセッションの git worktree もここに置くことで、リポジトリの入れ子(リポジトリの中に別の
  worktree が checkout される)を避けられる。

ディレクトリ名はリポジトリの realpath から作る `<basename>-<sha1 の先頭 8 文字>`。人間が見て分かる
basename と、同名リポジトリ(別クローン)を取り違えないためのハッシュを組み合わせている。

生成した claude settings(`claude-settings.json`)と system prompt もこの state ディレクトリ配下にあり、
リポジトリの外にあるため git diff ではレビューされない。自律実行セッションがこれらを直接書き換えて
自分の権限や制約を緩めることができてしまうと、`.agent/claude-settings.json` 側の deny だけでは
防げない抜け道になるため、生成物自身の絶対パスを `permissions.deny` に動的に追加して自己改変を禁じている
(`lib/settings.ts` の `generateSettings`)。

## パス解決を `root` と `agentRoot` の 2 系統に分ける

`lib/paths.ts` はリポジトリのパスを 2 系統に分けて解決する(`resolveRepoRoots`)。

- `root`: git 操作(worktree の作成・削除・ブランチ・マージ)と、上述の state ディレクトリ
  (`repoId` の算出元)の基準。linked worktree 内から実行しても、常に本体ワークツリーへ読み替える。
- `agentRoot`: `.agent/` 配下(config.json / tasks / decisions / human-review / archive /
  GOAL.md / OVERVIEW.md / PROMPT.local.md)の読み書きの基準。読み替えをせず、実行時の cwd
  (または `--repo` / `CCLOOP_REPO`)が指す作業ツリーそのものを使う。

分ける理由は、この 2 つが「読み替えるべきか」で逆の答えを持つため。git 操作と state ディレクトリは
worktree ごとに変えると意味が壊れる(worktree の追加・削除は本体でしか完結せず、worktree ごとに
別の repoId になると無関係な実行状態を参照してしまう)ので本体へ読み替える必要がある。一方
`.agent/` はタスクファイルなど「いま作業しているブランチの成果」そのものであり、本体へ読み替えると
worktree 内で `ccloop add` / `retry` / `abandon` を実行したときに無関係な本体側の `.agent/` を
書き換えてしまい、その worktree のブランチには乗らない(自律実行セッションの成果が自動マージに
反映されない事故につながる)。

この分離の結果、`ccloop status` / `list` / `add` / `retry` / `abandon` / `init` は worktree 内から
実行しても安全で、その worktree の `.agent/` だけを読み書きする。`.agent/` を触る処理を新しく足す
ときは `paths.root` ではなく `paths.agentRoot`(またはそこから作られる `agentDir` 系のフィールド)を
使うこと。一方 `ccloop run` は自分で worktree を作り
git 操作を `root` に対して行うため、linked worktree 内から起動すると `root` と `agentRoot` がずれて
壊れる。そのためリンクされた worktree 内から `ccloop run` を起動した場合はエラーで止め、本体の
ワーキングツリーへ移動するよう案内する。

## permissions 設計(`lib/settings.template.json`)

自律実行セッションは `node`/`npm` による任意コード実行が本質的に不可避なため、permissions で
セキュリティ境界を作ることはできない。セキュリティ境界は実行環境(devcontainer 等)側の責務であり、
permissions の役割は「うっかり・意図しない逸脱の防止」と「PROMPT.md が定めるワークフロー(worktree・
自動マージ・自己改変の禁止など)への誘導」に限定している。

permission mode は auto で起動しており、`permissions.deny` に一致しない操作は(allow の有無に関わらず)
実行できる。したがって実質のガードレールは deny リストであり、PROMPT.md の「絶対ルール」がセッションに
禁じている操作(ブランチ操作・push・自己改変対象ファイルの編集等)は permissions.deny にも同じ内容を
並べ、規律と機構の二重の担保にしている。

この二重化は片方だけが更新されると意味を失う(機械的には拒否されるのにセッションはそれを知らない、
あるいはその逆になる)ため、`lib/deny-consistency.test.ts` が一致を機械的に検査している。テンプレートの
deny パターンと、PROMPT.md「Bash 実行の権限制約」節の deny 箇条書きに現れる inline code トークンとの
対応表を持ち、双方向に網羅性を検査する形にしている。deny を増減させるときはテンプレート・PROMPT.md・
この対応表の三つを揃えて更新する。散文である PROMPT.md に文字列の完全一致を課さないための対応表であり、
表自体の陳腐化もテストで検知する。

allow は「読み取り専用で副作用が無い」操作に限定している。allow の役割は許可範囲を広げることではなく、
classifier の判定を経ずに即時実行できるようにする性能上の最適化でしかない(allow に無い操作も deny に
触れなければ classifier 経由で実行できる)。`Edit`/`Write` などのツールは allow に列挙が無くても
即時に通るため、あえて allow へ列挙していない。

パスを対象にした deny(`Read(path)` / `Edit(path)`)は対応するツールだけでなく、同じパスに触れる Bash
コマンド(`cat`・`cp` 等)にもクロス適用される。`Edit(path)` の deny だけで `Write` ツールによる
同一パスへの書き込みも止まるため、`Write(path)` を並べて重複させる必要はない。

## 壊れた `.agent/config.json` は既定値へ倒さず止める

`.agent/config.json` は人間が手で編集する前提のファイルである。項目の型や値が不正なとき黙って既定値へ
倒すと、人間が意図した設定と実際に動いている設定が食い違ったまま長時間ループが回り続ける。そのため
不正な項目を見つけたら、どの項目がどうおかしいかを列挙して止める(`normalizeConfig`)。1 件目で止めず
全項目を検査してからまとめて示すのは、直して再実行するたびに次の 1 件が出る往復を避けるため。

例外は「ファイルが存在しない」場合で、このときだけ完全な既定値を返す。config を読むのは Supervisor
本体だけでなく WorktreeCreate hook でもあり、hook が config の不備で落ちると worktree の作成自体が
できなくなるためである。「ファイルが無い」と「あるが壊れている」は区別し、後者は止める。

`triage` / `parallel` は例外的に寛容な正規化(範囲クランプ・既定値補完)のままにしている。これらは
値が多少ずれても動作の意味が変わらない性能パラメータであり、止めるほどの実害が無いため。

診断コマンド(`ccloop doctor`)と `ccloop status` はこの規則の対象外で、config が壊れていても落ちない。
壊れた状態を人間が調べるための道具が、壊れているせいで使えなくなっては本末転倒だからである。

## 停止を Ctrl+C のみ・オンメモリにした理由

`ccloop run` の停止は、実行しているプロセスへの Ctrl+C(SIGINT)の段階的なエスカレーション
(1 回目: 新規セッション停止 → 実行中の完了待ち、2 回目: 緊急停止(SIGTERM → 猶予後 SIGKILL)、
3 回目: 即 SIGKILL)だけで完結し、`STOP` ファイルのような永続的な停止指示ファイルは存在しない。

- 停止状態をファイルとして永続化すると、消し忘れたまま次回 `ccloop run` を実行したときに
  「なぜ動かないのか」が分かりにくくなる。プロセスが生きている間だけ有効な状態にすることで、
  次に `ccloop run` を実行すればそのまま動く単純な挙動にできる。
- 複数リポジトリで同時に ccloop を動かす運用を考えたとき、ファイルベースの停止指示は
  「どのリポジトリの停止か」の対応関係を別途管理する必要が出る。プロセス単位の Ctrl+C なら
  対応関係は自明。

## clean 停止でも衝突解消セッションだけは起動する理由

1 回目の Ctrl+C(clean)は「新規セッションを起動しない」が原則だが、衝突解消セッションだけは例外で、
実行中セッションが尽きたあとも 1 本ずつ起動してから停止する。

タスクセッションの成果を main へマージして衝突すると、Supervisor は衝突を再現した状態
(マージ進行中・衝突マーカーあり)の worktree を残す。この状態を前へ進める手段はセッションの起動しかない
(Supervisor 自身は衝突を解消しない)。ここで即座に停止すると、中断状態を抱えた worktree が
次回 `ccloop run` まで宙に浮き、「Ctrl+C 直後にたまたま衝突したかどうか」で残骸の有無が変わる。
停止の直前に片付けておけば、停止後のリポジトリの状態が予測しやすくなる。

例外には 2 つの上限を課している。同時に起動するのは 1 本まで(解消セッションを並列に走らせると
解消セッション同士が再び衝突しうる)、かつタスクごとに停止指示後 1 回まで(解消セッションが再び
衝突しても停止が無限に延びない)。上限に達した分は worktree を残したまま停止し、その旨をログに出す
(次回の `ccloop run` が同じ worktree で解消を再開する)。それでも待てない場合はもう一度 Ctrl+C すれば
緊急停止に落ちる。

この起動判断はスヌーズ中のタスクも対象にする。スヌーズは「今そのタスクの本来の作業をしても
空振りする」という申告であり、人間の入力待ちなど再開しても進められない状況を表す。一方、衝突解消
セッションの仕事は衝突マーカーの解消・検証・コミットという機械的作業で、スヌーズが待っている入力
とは無関係に進められるため空振りにあたらない。無視できるのは停止直前のこの経路だけで、通常周回の
選定はスヌーズを尊重する。

起動しても確実に失敗する状況では例外を適用しない。rate limit 中は解除を待ってから起動する(解除は時間で
来るため、待てば例外の目的を果たせる)。起動直後のクラッシュが連続している(環境要因が疑われる)場合は
起動を諦めて停止する。停止処理中は他に起動するセッションが無く、連続クラッシュの記録を解消する機会が
無いため、待っても待ち続けるだけになるからである。

## セッションの基準は main ではなく自分の HEAD である

タスクセッションの worktree ブランチは起動時点の main から作られるが、main はセッションの実行中も
他のタスクのマージによって進む。したがってセッションから見た `main` は「自分の親」ではなく
「自分より先に進んだ別の状態」であることが普通である。

この差は、退避ブランチに取り残された成果を後から取り込む作業(救出)で問題になる。`git diff
main...<退避ブランチ>` の結果を自分の worktree へ当てると、退避ブランチが分岐した後に main へ
入った変更まで巻き戻してしまうことがある。退避ブランチ側が衝突解消の過程で main の内容を
落としていた場合、その取りこぼしをそのまま再現するためである。しかも自分の HEAD を基準にすれば
無害な差分と見分けがつかないので、`git diff main` で確認しても判断を誤る。

救出時に見るべきは常に `git diff HEAD` である。main に入っている変更は、セッション終了後の
自動マージで合流する。セッションが手で持ち込む必要はない。

## worktree の「衝突解消待ち」判定を 1 つの述語に集約する理由

worktree に中断された git 操作が残っているかの判定は、ライフサイクルの各段階に散っている
(セッション終了時に worktree を残す / 起動時のリカバリで保持する / 再開対象のタスクを選ぶ /
再開セッションに衝突解消の指示を注入する / `ccloop status` に表示する)。これらは同じ状態を
指していなければならず、1 箇所だけ条件を変えると「worktree は残されたのに再開対象として
選ばれない」あるいは「保持されるべき worktree が統合処理へ進んで破棄される」という、
症状からは原因の見えない不整合が生まれる。そのため判定は `worktreeConflictPending` に集約し、
呼び出し側で条件を書き分けない。

判定対象は merge だけでなく cherry-pick・revert・rebase・bisect の中断も含む。セッションの
permissions は merge・rebase・reset を禁じている一方 cherry-pick と revert は禁じておらず、
セッションがこれらを中断したまま終了する経路が実在するため。

一方リポジトリ本体(main)側の判定は merge に限定したままにしている。あちらは `MERGE_HEAD` の
中身を読んで「Supervisor 自身の自動マージの中断か、人間が手で始めたマージか」を見分ける処理で、
他の操作には対応する読み先が無い。worktree 側と main 側で判定が異なるのは意図的である。

## 機械的に解決するマージ衝突の範囲

自動マージで衝突したとき、Supervisor が機械的に解決するのは「並行実行が正常な運用として引き起こす衝突」
だけで、それ以外はすべて人間に回す(マージを abort して worktree を残す)。基準は
「セッションの意図を推測せずに、正しい結果を一意に決められるか」である。

対象は 2 種類ある。

- **担当タスクファイル `.agent/tasks/<taskId>.md`**: Supervisor は試行履歴を main 側へ追記し、
  セッションはブランチ側で同じファイルの status や進捗を書き換えるため、正常な運用で必ず衝突する。
  セッションが書いた最終状態が常に新しいので、ブランチ側を採用すれば一意に決まる。
- **`.agent/decisions/index.md`**: 未掲載の決定を index へ載せるのはセッションの手作業ではなく、
  ローテーションのリコンサイル(`lib/rotate.ts`)が main 側で機械的に行う。それでも人間の手編集や
  セッションの直接編集で同じ領域が触られうるため、安全網としてエントリを ID で突き合わせた
  3-way マージで解決する。
  和集合ではなく 3-way にするのは、ローテーションがアーカイブ済みエントリを index から消すためで、
  和集合ではアーカイブ済みの決定が復活してしまう。並び順はローテーションのリコンサイルと同じ
  ID 降順に揃える(順序が違うと解決直後の index が次回ローテーションで毎回書き換えられる)。
  ヘッダ・フッタは人間が書いた文章なので、両側で別々に変更されていれば統合を諦めて人間に回す。

逆に `.agent/decisions/` `.agent/human-review/` 直下の個別ファイルの同名 add/add は機械的に解決しない。
ID に日時と slug を含めるため偶然の衝突は起きず、同名になるのは二重起票のときだけで、
どちらを残すかは内容を読まないと決められないからである。

片付け(ローテーション + 退避パッチの掃除)は「実行中セッションが 0 の周回」と「探索セッションの
起動直前」の 2 箇所を契機に行う。前者だけだとタスクが途切れず周回が来ない状況で記録が溜まり
続けるため、後者を追加している。ローテーションは走行中のタスクセッションが担当するタスクの記録
だけ対象から外す。担当タスクファイルは上記のとおりブランチ側が正として自動マージされるため、
main 側で先に archive へ移動すると modify/delete の衝突になる。decisions / human-review は
走行中セッションが「終わったもの」を書き換える経路が無いため、除外しなくても衝突しない。

## タスクファイルの解消方針が自動と手作業で逆になる理由

担当タスクファイルの衝突を、自動マージ(`resolveMechanically`)はブランチ側を採用して解決するが、
衝突解消セッションへの指示は逆に「main 側を土台にせよ」と言う。矛盾ではなく前提が違う。

自動マージが扱うのは「衝突が担当タスクファイルと `decisions/index.md` だけ」という、その場で
一意に決まって 1 回で終わる状況である。セッションが書いた最終状態が常に新しいので、ブランチ側が正しい。

セッションに回るのは、それ以外の実質的な衝突が混ざって自動解決を諦めた状況である。この場合は
解消してもマージ成立までに main がまた進みうるため、繰り返しが前提になる。ここでブランチ側の
「## 試行履歴」を残すと、ccloop が main 側の同じ末尾へ書く機械記録と次のマージでまた衝突しうる
(両側が同じ挿入点へ追記する限り、正しい 3-way マージでも必ず衝突する)。

ただし再衝突しても、衝突リトライはタスク本来のやり直し回数(`retries`)とは別枠
(`conflictRetries` / `maxConflictRetries`)で数えるため、成果が完成しているのに失敗扱いになる
事故は起きない。一方で試行履歴を捨てると、次の試行が「何を確認済みで、何を試して駄目だったか」を
失い同じ調査をやり直すことになり、代償のほうが大きい。よって通常は main 側の機械記録を
ブランチ側へ取り込んだ上で試行履歴を残したまま解消してよい。ブランチ側を main と同一内容へ
寄せて記録を捨てるのは、実質的な衝突が短い間隔で繰り返し、衝突リトライの上限まで使い切る
恐れがあるときの最終手段とする。

## 追記専用ファイルは union マージに任せる

`CHANGELOG.md` のように「同じ節へ各ブランチが独立に 1 行足す」ファイルは、3-way マージでは
片側がもう片側のスーパーセットであっても必ず衝突する。しかも解消しても main が進むたびに
同じ場所でまた衝突するため、衝突解消を繰り返すほど不利になる。両側の項目をどちらも残すのが
常に正しい以上、人間やセッションに判断を求める意味が無いので `.gitattributes` の
`merge=union` で git に任せる。

union は衝突を報告せず両側の追記を機械的に残す方式なので、節の構造が片側だけで変わったとき
(リリースで「## 未リリース」が版番号の見出しへ繰り上がった直後など)に行が意図しない節へ
入りうる。静かに間違う方向の失敗なので、リリース直後は並びを目視で確認する。

`.gitattributes` はマージを実行する側のツリー(= main)に存在して初めて効くため、ブランチ側だけに
足しても、それが main へ入るまでは効かない。またこの指定は ccloop 自身のリポジトリのものであり、
`ccloop init` は利用側リポジトリへ `.gitattributes` を作らない(利用側に残すのは `.agent/` だけ)。
利用側で変更履歴を持つなら同じ指定を自分で足すとよい。

## 瞬時クラッシュの連続による起動抑制(crash-backoff)

起動直後に異常終了するタスクセッションが 3 回連続すると、環境要因による系統的な故障を疑い、起動可能な
状況でも 1 周回だけ新規セッションの起動を見送る。この抑制は恒久的なものではなく、待機明けに連続回数を
0 へ戻して次周回からは通常どおり起動する(抑制中はセッションが起動しないため、待機明け以外に連続回数を
解消する経路が無い)。レートリミットによる終了は時間経過で解決する事象であり、環境要因の故障でも復旧の
証拠でもないため、この連続回数には数えない。ただし上記の clean 停止処理中だけは待機明けでもリセットしない:
連続クラッシュを解消しないまま起動を諦めて停止する設計を保つためである。

数えるのはタスクセッションだけで、探索セッションの瞬時クラッシュは対象外である。この抑制は「実行可能な
タスクがある」ことを発火条件にするため、探索しか走らない状況では数えても抑制が起きない。その状況でも
探索の空回りは別の仕組みで塞がれている(瞬時クラッシュした探索は同じプロセスの中では
`explore.minIntervalMs` が経過するまで再探索しない)ので、ループはアイドル終了か待機へ落ちる。
逆に数えると、タスクセッションが健全でも探索固有の失敗で
タスク起動と(停止時の)衝突解消まで抑制する誤検知になる。

## 探索セッションが並列枠を消費し、こまめに割り込まない理由

探索セッション(Opus によるフル探索)は並列枠(`parallel.maxSessions`)を 1 つ消費し、実行中は
新しいタスクセッションを起動しない(走行中の既存タスクセッションは止めない)。空き枠があるときだけ、
次のいずれかの条件で走る。

- アイドル時: 実行可能タスクが無く、前回探索以降に main(タスクのマージ、またはタスクの失敗確定)
  または入力(GOAL.md / Human Review 回答)が変化したか、一度も探索していない。ただし直前の探索が
  空振り(新規タスクなし)なら `explore.minIntervalMs` のクールダウンが経過するまで待つ。
  クールダウンは「同じ入力での再探索」を抑えるためのものなので、新しい人間の入力には掛からない。
  ただし直前の探索が起動直後に異常終了した(瞬時クラッシュ)場合はこの免除も働かない。瞬時クラッシュ
  した探索は GOAL.md / Human Review の回答を確認済みとして記録しない(次回の探索が改めて取り込む)
  ため、`minIntervalMs` のクールダウンが経過するまでは人間の入力があっても再探索しない。この抑制は
  プロセス内でのみ効く。`ccloop run` を起動し直すと外れ、未取り込みの入力に対して即座に再探索する
  (人間が原因を直して打ち直したときに待たされないことを優先している。逆に、外部の自動再起動の下に
  置くと、クラッシュが続く間は再起動のたびに探索が起動しうる)。
- 実行可能タスクがある間: 前回探索から `minIntervalMs` 以上経過し、かつ main または入力が変化して
  いれば、空いた枠へ次のタスクを起動する前に探索を 1 回挟む。

GOAL.md や Human Review 回答の変化そのものは探索を即座には割り込ませない(triage の軽量モデル判定は
従来どおり即時に走る)。次に枠が空いたタイミングで 1 回にまとめて(coalesce)消化される。

- 探索は Opus のフル探索でトークンコストが大きい。回答・タスク完了のたびに敏感に反応すると、
  コストが走行時間に比例して膨らむ。探索の目的は「次に起動するタスクが最新の GOAL / main を
  反映していること」であり、次のタスクを始める直前に済んでいれば十分で、変化の瞬間に反応する
  必要はない。
- 探索は既存タスクの書き換え・取り下げを行うため、他のセッションと同時に起動すると、古いタスクを
  起動したり、セッションが読んだ直後のタスクファイルを書き換える競合が起きる。そのため探索走行中は
  新規起動を止める。
- 既存の走行中セッションまでは止めない(走行中のセッションの完了を待って main を静止させる方式は
  採らない)。探索は main の完全な静止スナップショットを必要とせず、探索中に入ったマージは
  次回の探索で吸収されるため。
- トレードオフとして探索中は空き枠が埋まらない。空き枠が埋まらない時間は `minIntervalMs` あたり
  最大で「探索 1 本分の時間 × 空いた枠数」に収まるため許容する。

## `dependsOn` でなく `installsAfter` を使う理由

`features/ccloop/devcontainer-feature.json` は git / node / claude-code の各 feature を
`installsAfter` で指定しており、`dependsOn` ではない。ccloop feature は git / Node.js / `claude` CLI を
自分ではインストールしない(前提として要求するだけ)ため、`dependsOn` で「無ければ入れる」機能は
不要で、必要なのは「これらの feature が(利用側の設定で指定されているなら)先に完了していること」
という順序保証だけである。存在確認は実行時に `ccloop doctor` が担う。

## CI の `src -> features` シンボリックリンク

`devcontainer features test` は `--base-path-to-features` のような publish 時のオプションを持たず、
`--project-folder` 配下の `src/<feature>` 固定でしか feature を探せない。このリポジトリは feature を
`features/ccloop` に置いている(`src/ccloop` ではない)ため、CI(`feature-test` ジョブ)では
`ln -s features src` でブリッジしてから `devcontainer features test` を実行している。ファイルの複製・
移動はしない。

## Node の型ストリップ前提(`erasableSyntaxOnly`)

ccloop は `.ts` をビルドせず Node の型ストリップ機能で直接実行する(`bin/ccloop` が
`node ... cli.ts` を直接叩く)。`tsconfig.json` の `erasableSyntaxOnly: true` は、型ストリップでは
消せない TypeScript 構文(enum、パラメータプロパティ等)の使用を型検査の時点で禁止し、
「型チェックは通るが実行時にストリップできない」コードが紛れ込むのを防ぐ。ビルドステップを持たない
ことで、feature のインストールが `lib/` と `bin/` のファイルコピーだけで完結する(コンパイル済み
成果物の生成・配布を気にしなくてよい)。この前提により、実行環境には型ストリップが既定で有効な
Node.js のバージョン(24 以上、または 22.18 以上)が要る。

## テスト実行元セッションの環境変数を継承しない理由

このリポジトリは ccloop 自身で自律運用されているため、`npm test` を実行するセッション自体が
`CLAUDE_AGENT_SESSION_KIND` / `CLAUDE_AGENT_AUTONOMOUS` / `CLAUDE_AGENT_TASK_ID` などの環境変数を
持っている。テストコードは Supervisor が spawn する hook やコマンドの挙動を検証するために子プロセスを
起動するが、その env を素の `process.env` から組み立てると、実行元セッションが持つこれらの変数が
そのまま漏れ込み、被テストコード側の「セッション種別による分岐」を検証意図と無関係に変えてしまう。

そのため vitest の setupFiles(`lib/test-setup.ts`)で `CLAUDE_AGENT_*` を一括削除し、各テストが
明示的に指定した値だけが子プロセスに渡るようにしている。これにより `npm test` は実行元セッションの
状態(対話セッションか、どのタスクを担当しているか等)に依存せず再現可能になる。

## テストがリポジトリ本体を書き換えないことを機械的に担保する

このリポジトリのテストは、Supervisor が実際に行う操作——worktree の作成、`agent/<taskId>` ブランチの
作成・削除・改名、main へのマージ——を検証対象にしている。各テストは一時ディレクトリに使い捨ての
git リポジトリを作ってそこへ向けるが、対象ディレクトリの解決がどこかで既定値へ落ちると、git は
**テストを実行している開発者のリポジトリ本体**に対して走る。このとき症状はテスト失敗ではなく、
「テストは緑のまま、手元のリポジトリに知らないブランチが増えている」である。誰も消さないので溜まり、
`agent/` 名前空間に残ったものは Supervisor の孤児ブランチ回収と見分けがつかなくなる。

この失敗モードには三段で備えている。

- **引数で受け取る**: worktree やブランチを作成・削除・改名・マージする関数は、対象リポジトリの
  ルートを引数で受け取り、既定値を持たない。`lib/supervisor.ts` にはモジュール共有の `repoPaths()`
  があり未確定なら cwd から解決するが、このフォールバックに依存してよいのは設定・タスク・state の
  読み書きまでである(対象を取り違えても履歴は壊れない)。破壊的操作までこれを既定値にすると、
  安全性が「呼び出し側が毎回テスト用のリポジトリを注入し忘れないこと」だけに依存する。
  タスクセッションの終了処理では、対象ルートを起動時の文脈(`TaskSessionContext`)に載せて
  持ち回している。
- **fail-closed**: worktree・ブランチを作る経路(`lib/hooks/worktree-create.ts`)は、対象リポジトリが
  明示されていないときに `process.cwd()` へフォールバックせずエラーで落ちる。隔離の漏れが
  「静かに本体を汚す」ではなく「即座に失敗する」に変わる。
- **事後検出**: vitest の globalSetup(`lib/test-global-setup.ts`)がテストラン前後でブランチ一覧を
  比較し、増えていればテストラン全体を失敗させる。fail-closed をすり抜けた未知の経路もここで捕まる。

事後検出では、増えたブランチのうち `.agent/tasks/` または `.agent/archive/tasks/` に対応する
タスクファイルが実在するもの(`agent/<taskId>` と衝突退避用の
`agent/conflict/<taskId>-<圧縮タイムスタンプ>` の両方)を除外している。このリポジトリは自分自身で
自律運用されているため、テスト実行中にも別セッションが正当な作業ブランチを作る。それを事故と区別
するには「対応するタスクが存在するか」を見るのが最も確実で、これは Supervisor の孤児ブランチ判定と
同じ基準である。減ったブランチを無視するのも同じ理由で、こちらは孤児ブランチ回収や他セッションの
後片付けが正常に働いた結果である。

検出時に teardown から例外を投げてはならない。vitest は globalSetup の teardown で発生した例外を
`error during close` として出力するだけで終了コードを変えず、**テストランは成功扱いのまま終わる**。
それでは「緑のまま本体が汚れる」という、この仕組みが防ごうとしている状態そのものになる。
`process.exitCode` を明示的に立てて失敗させること。

## hook は「無音で無効化される」ため入出力契約をテストで固定する

`lib/hooks/` の各スクリプトは Claude Code が settings.json の記述に従って起動する。ここで壊れたときの
症状は例外やテスト失敗ではなく、**何も起きなくなること**である。たとえば `deny-ask-user.ts` が返す JSON の
キー名(`hookSpecificOutput.hookEventName` / `permissionDecision`)がずれても、Claude Code は
それを解釈できないまま黙って通す。結果は「自律実行セッションが人間の回答待ちで停止する」——
その hook が防ごうとしている事態そのものである。

この失敗モードは他のテストでは検知できないため、hook については次の 2 段を明示的に固定している。

- スクリプト単体の入出力契約: 子プロセスとして起動し、出力 JSON のキー名と値、不正入力の拒否、
  終了コードを検証する(`lib/hooks/*.test.ts`)。テストは hook ファイルの隣に置く。
  `lib/worktree.ts` のような下請けの検証はそちらのテストに任せ、hook 側では重複させない。
- `lib/settings.template.json` への登録: スクリプトパスが含まれることだけを文字列一致で見ると、
  エントリが別の hook イベント配下へ移動しても matcher が変わっても通ってしまう。
  イベント種別・matcher・command の結び付きをオブジェクトとして辿って検証する(`lib/settings.test.ts`)。

静的に担保できるのはここまでで、「Claude Code が settings.json の記述どおりに hook を発火させること」は
外部依存であり、このリポジトリのテストでは検証できない。

## `.agent/` 記録ファイルの ID を連番でなく日時 + slug にする理由

`.agent/tasks/` `.agent/decisions/` `.agent/human-review/` の ID(= ファイル名)は
`<prefix>-<YYYYMMDD>-<HHMM>-<slug>` の形式で、連番ではない(形式の詳細は
[lib/prompt/PROMPT.md](../lib/prompt/PROMPT.md) を参照)。

- 連番は「既存ファイルの最大番号 + 1」で決まるため、複数の worktree で並行して動くセッション同士が
  同じ番号を採番して衝突しやすい。衝突するとマージ時にどちらかを改番する必要があり、改番すると
  本文中の ID 参照(`dependencies` / `tasks` / `review` など)も追従して書き換えなければならない。
  日時を ID に含めることで採番だけでは衝突しなくなり、マージ時の改番ロジック自体が不要になる
  (同名ファイルの add/add はその場で解決できない実質的な内容衝突として、通常のコンフリクトと
  同じく人間に回す)。
- slug を加えることで、人間が `ls` や `git log` の一覧を見ただけで各ファイルの内容を推測できる
  (連番だけでは中身がファイルを開くまで分からない)。
- slug は ASCII の名詞句限定(`^[a-z0-9]+(?:-[a-z0-9]+)*$`)にしている。ID はブランチ名
  `agent/<taskId>` にそのまま使われ、`grep`/`ls` での扱いやすさも重要なため、シェルやブランチ名で
  安全に使える文字集合に制限している。
