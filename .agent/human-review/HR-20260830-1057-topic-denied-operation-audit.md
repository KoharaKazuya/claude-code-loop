## 確認事項

一言でいうと: **あなたが明確に禁止した操作(`git push` や `sudo` など)をエージェントが
試みたとき、その事実を記録して `ccloop status` に出すようにしてよいか。**

### なぜ聞いているか

改善のネタごとに確認を取る運用にしている。これは `ccloop status` の表示内容が変わる話で、
変更履歴に 1 行載る粒度に当たる。

### いまどうなっているか

エージェントの操作が許可されずに止まる場面には 2 種類ある。

1. **その場の判定で止まったもの**(書き込み系の操作などを毎回判定している)。
   これは記録され、`ccloop status` に「直近 7 日の permission 拒否 N 件(セッションは代替手段で
   続行済み。回答不要)」として件数が出る。
2. **あらかじめ禁止リストに入っているもの**(`git push` / `checkout` / `merge` / `rebase` /
   `reset` / `clean` / `stash` / `worktree`、ブランチの削除・改名、`sudo`、設定ファイルの編集など)。
   **こちらは意図的に記録されていない。** 「人間が既に禁止と決めたものだから」という理由が
   コードにコメントとして書かれている。件数は実行ログに 1 行書き捨てられるだけで、
   `ccloop status` にもリポジトリ内のどのファイルにも残らない。

つまり **最も破壊的なカテゴリの操作を試みた事実だけが、どこにも残っていない。**

### 何が困るか

自律運転を任せている側からすると、「エージェントが本流への push や `sudo` を試みたか」は
いちばん知りたい情報のはずだが、いま知る手段が無い。試みが増えているなら、指示の書き方か
タスクの立て方に問題があるという兆候にもなる。

もう 1 つ、**説明と実装が食い違っている。** セッションに渡している共通ルールには
「拒否の事実は ccloop が記録し `ccloop status` に要約が出るので、セッションが人間へ報告する
必要はない」と書いてある(`lib/prompt/PROMPT.md`)。禁止リスト一致の拒否については
これが成り立っていない。エージェントは「記録されているはず」と信じて何も残さないので、
**二重に消える。**

### やるとしたら何をするか

禁止リストに一致した拒否も記録し、`ccloop status` では

- 「その場の判定で止まったが代替手段で続行済み(回答不要)」
- 「明示的に禁止した操作を試みた(参考情報)」

の 2 つに分けて件数を出す。記録の置き場と形式は既存のものを流用できるので、
作りは大きくならない見込み。

### 気にしている点(ここが確認したい理由)

**そもそも記録しないのは意図的な設計である。**「禁止済みなのだから、試みたことをいちいち
報告しても人間にできることは無い」という考え方には筋が通っている。表示を増やせばそのぶん
1 件あたりの重みは薄まる。**監査の価値を取るか、表示の静けさを取るかの判断であり、
これは好みの問題なので勝手に決めない。**

### やらない選択もある

記録しないままにして、代わりに共通ルールの記述のほうを実態に合わせて直す(「禁止リスト一致の
拒否は記録されない」と正確に書く)。食い違いは消え、表示は増えない。

## 暫定判断

回答があるまでこのトピックのタスクは作らない。ただし説明と実装の食い違いを放置すると
エージェントが誤った前提で動くため、**回答が無いまま次の探索まで持ち越した場合は、
共通ルールの記述を実態に合わせる小さな修正だけ先に行う**(表示は変えない)。

## 回答してほしいこと

**明示的に禁止した操作をエージェントが試みた事実を、記録して `ccloop status` に出してよいか。**
(出さない場合は、共通ルールの記述を実態に合わせて直すだけにする。)
