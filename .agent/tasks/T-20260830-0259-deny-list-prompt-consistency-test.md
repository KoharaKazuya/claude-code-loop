所属フェーズ: 現在フェーズ内の検証強化。機能追加ではない。

## 目的

`.agent/GOAL.md` の制約に「permissions の deny リストと PROMPT.md の絶対ルールは常に一致させる
(二重の担保)」とあるが、**この一致を検証する仕組みが存在しない**。

- `lib/settings.template.json` の `permissions.deny`(22 件)と、
  `lib/prompt/PROMPT.md` の「Bash 実行の権限制約」節に列挙された deny 一覧は、
  調査時点では内容が一致している(確認済み)。
- しかし `lib/settings.test.ts` はテンプレート自体の構造しか見ておらず、
  `lib/prompt.test.ts` は PROMPT.md の連結処理しか見ていない。両者を突き合わせるテストは無い。

この二重化は「機械的な強制(deny)」と「セッションへの説明(PROMPT.md)」を両輪で効かせるための
設計である。片方だけが更新されると、機械的には拒否されるのにセッションはそれを知らない(あるいは
その逆)状態が生まれ、セッションが拒否を踏んでは迂回を試みる・BLOCK 判断を誤るといった形で
無人運用の質が落ちる。ズレても誰も気づけない現状が問題である。

## 対象

- `lib/settings.template.json`(`permissions.deny`)
- `lib/prompt/PROMPT.md`(「Bash 実行の権限制約」節の deny 一覧)
- テストの追加先は `lib/settings.test.ts` か新規ファイルのいずれか。実装時に判断する。

## 完了条件

- 両者の deny 内容がズレたときに落ちるテストを追加する。
- テストの粒度は実装時に判断してよいが、次を満たすこと。
  - PROMPT.md 側は散文であり deny パターン文字列をそのまま列挙しているわけではないため、
    文字列の完全一致を強いる設計にしない。維持できない厳格さは、将来の編集者が
    テストを緩める方向へ倒れる原因になる。
  - 一方で「テンプレートに deny を足したのに PROMPT.md に書き忘れた」を検知できること。
    最低限、各 deny エントリの識別子(コマンド名・パス断片など)が PROMPT.md の該当節に
    現れることを確認する、といった実効性のある検査にする。
  - 逆方向(PROMPT.md にあるがテンプレートに無い)も検知できることが望ましい。
    実現が難しい場合は、なぜ難しいかをテストのコメントに残す。
- 対応関係の判定に恣意的なマッピング表を書く場合は、その表自体が陳腐化しうるため、
  表に無いエントリが現れたらテストが落ちるようにする(黙って素通りさせない)。
- `npm run typecheck` / `npm run lint` / `npm run test` が通る。
- 設計判断(検査の粒度をどう決めたか)を `.agent/decisions/` に記録する。

## 補足

`lib/settings.ts` は state ディレクトリの絶対パスに対する deny を実行時に動的追加している
(生成された settings.json / system prompt への自己改変禁止)。パスがリポジトリごとに変わるため
テンプレートに書けないという正当な理由があるので、この分をテンプレート不足として扱わないこと。
