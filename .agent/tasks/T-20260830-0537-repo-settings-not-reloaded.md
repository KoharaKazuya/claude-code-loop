所属フェーズ: 4(思いつく改善すべて)。文書が明言している挙動と実装が食い違っている修理であり、
人間への確認は取らずに進めてよい。

## 何が起きているか

### (1) 追記した権限が反映されない

`README.md:162` は「どちらもセッション起動時に読まれるため、次に起動するセッションから
反映される」と書き、`lib/prompt/PROMPT.md:78` も「この設定はセッション起動時に読まれるため、
次のセッションから反映される」と自律セッションに教えている。

実際には `generateSettings(repoPaths())` の呼び出しはコードベース中に 1 箇所
(`lib/supervisor.ts:3271`)しかなく、`mainLoop` の `while (true)`(同 3338 行)に入る**前**に
一度だけ実行される。各セッションの起動時に渡しているのは
`--settings <generatedSettingsPath>` という固定パスだけで(`lib/supervisor.ts:1762-1763`)、
中身の読み直しも再生成もしない。同 1767 行のコメント自身が「ファイルの生成は run の起動時に
1 回」と明記している。

つまり反映の単位は「セッション」ではなく「`ccloop run` プロセス」である。動かしっぱなしの
ループの下では、人間が `.agent/claude-settings.json` に許可を追記しても効かない。
`generateSystemPrompt`(同 3273 行)も同じ位置にあるため、`PROMPT.local.md` の編集も同様。

### (2) 壊れていても無音

`readRepoSettings`(`lib/settings.ts:85-92`)は `JSON.parse` の失敗を `catch {}` で握りつぶし
`null` を返すだけで、ログを出さない。同じ設定まわりでも `loadDenyRules`
(`lib/supervisor.ts:1953-1966`)は失敗時に必ず `log(...)` で警告しており、扱いが非対称である。
`doctor` にも `claude-settings.json` の妥当性検査は無い(grep で該当なし)。

## 実害

権限で拒否された作業を人間が許可して再開させる、という **BLOCK からの復旧フローそのもの**が
動かない。しかも失敗は完全に無音で、ログにも `ccloop status` にも何も出ない。人間から見ると
「許可を書いたのに、次のセッションもまた同じ理由で止まる」という状態が原因不明のまま続く。
(1) と (2) は原因が違うだけで、人間が観測する症状は同一である。

合成そのものは安全側に倒れている(壊れた追記があっても既定の deny は保たれる)ことは確認済みで、
セキュリティ上の穴ではない。

## やること

1. (1) を直す。文書が書いている「次のセッションから反映される」が正となる方向で直すこと。
   GOAL が掲げる「人間の確認・介入の導線」の根幹であり、文書側を実装に合わせて書き換える
   (「run を再起動するまで効かない」と明記する)方向は採らない。
   セッション起動のたびに `generateSettings` / `generateSystemPrompt` を呼び直す形が素直だが、
   起動時 1 回にしてある理由がコメント以外にあるかを確認してから決める。書き出しは
   `.tmp` + rename で原子的なので、走行中の別セッションが読んでいる最中に差し替わっても
   壊れないことを確認すること。
2. (2) を直す。`readRepoSettings` が JSON の解析に失敗したときは `loadDenyRules` と同様に
   警告をログへ出す。合成の結果(テンプレートのみへのフォールバック)は変えない。
3. `lib/settings.test.ts` に (2) のテストを足す。(1) は再生成の呼び出し位置が変わることを
   検証できる形でテストする。
4. 利用者から見た挙動が変わるので `CHANGELOG.md` の「## 未リリース」に 1 行足す。
   「権限の追記がループを動かしたまま効くようになった」という利用者の言葉で書くこと。
