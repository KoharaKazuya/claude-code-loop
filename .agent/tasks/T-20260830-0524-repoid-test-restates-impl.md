人間への事前確認は不要(`CHANGELOG.md` にも載せない)。

## 目的

`lib/paths.test.ts` の `repoId` フォーマット検証を、実装から独立した期待値に置き換える。
あわせて `repoId` の `realpath` 解決(シンボリックリンク経由のパス)に対する検証を追加する。

## 現状の問題

`lib/paths.test.ts:174-178` が期待値を

```
`${path.basename(dir)}-${createHash("sha1").update(dir).digest("hex").slice(0, 8)}`
```

という式で、その場で計算している。これは `lib/paths.ts:155-158` の実装とハッシュ関数・スライス長・
結合順まで一字一句同じ式であり、テストが保証しているのは「実装が自分自身を再現していること」だけである。
アルゴリズム(sha1・先頭 8 桁・`basename-hash` の順)が意図せず変わっても、この式ごと追随している限り
検知できない。

もう 1 点、このテストが使う `dir` は共通の `beforeEach`(`lib/paths.test.ts:21` 付近)で
`fs.realpathSync(fs.mkdtempSync(...))` により既に正規化済みのパスである。そのため実装内の
`realpath(root)` 呼び出しが本当に効いているか(シンボリックリンク越しのパスでも同じ ID になるか)は
検証されていない。調査時点で `repoId(` の呼び出し箇所 5 件はすべて正規化済み、または同じ手順で
生成したパスだった。

これは状態ディレクトリの同定に使われる関数なので、逸脱すると「同じリポジトリが別リポジトリ扱いになる」
「別リポジトリが同じ状態ディレクトリを共有する」といった実害につながりうる。

## 完了条件

1. `repoId` のフォーマット検証が、固定の入力文字列に対する事前計算済みのリテラル期待値
   (実装と同じ式をテスト内で再計算しない形)で行われている。
2. シンボリックリンク経由のパスを `repoId` に渡しても、リンク先の実体パスから導出した ID と
   一致することを検証するテストがある。
3. `npm run` 経由で typecheck / lint / テストが通る。
4. 検証を弱めない(既存アサーションの削除・緩和はしない)。

## 補足

テスト全体の質は高く、モック過多・アサーション欠落・例外無視のみの確認といった典型的な
「見せかけのテスト」は他に見つかっていない。本タスクは見つかった唯一の具体的な穴である。
