## 目的

系統故障(claude コマンドの設定ミスなど)で起動直後に落ち続ける状況を、探索セッションしか
走っていないときに検知できるかどうかを確定し、必要なら塞ぐ。

## 現状(調査で判明した範囲)

`runExploreSession`(`lib/supervisor.ts:2673-2721` 付近)は `finishTaskSession` と違って
`fastCrashStreak` を更新しない。`lib/supervisor.ts:894-903` のコメントは更新箇所を
「finishTaskSession と mainLoop の 2 か所」と明記しており、探索をスコープ外にするのは
意図的な設計にも読める。

一方、実行可能なタスクが 1 つも無い状態では走るのは探索セッションだけになる。この状態で
探索が起動直後に落ち続けると、crash-backoff による系統故障検知が働かず、空振り探索の
クールダウン(`exploreDue`)だけが歯止めになる。無限に速く回ることはないが、故障として
表面化しないままループが空回りし続ける可能性がある。

**この「意図的なスコープ設定なのか見落としなのか」はコードとコメントからは断定できていない。**
まずそこを確定させるのがこのタスクの主目的である。

## 完了条件

次のどちらかで終える。

- **意図的だと確認できた場合**: 根拠(コメント・テスト・設計上の理由)を添えて
  `.agent/decisions/` に記録し、`lib/supervisor.ts:894-903` のコメントに「探索セッションを
  対象外とする理由」を一行足す。実装は変更しない。
- **見落としだと確認できた場合**: 探索セッションの瞬時クラッシュも系統故障検知の対象に含め、
  その分岐を検証する回帰テストを足す。判断と理由を `.agent/decisions/` に記録する。

いずれの場合も `npm run` 経由の test / typecheck / lint が通ること。

## 制約

修正を選ぶ場合、`ccloop run` の停止条件(いつループを諦めるか)は利用者から見た挙動なので、
既存の crash-backoff の閾値・停止条件そのものは変えない。変える必要が出たと判断した場合は
実装せず、その判断を `.agent/decisions/` に記録したうえでこのタスクを `blocked` にし、
`.agent/human-review/`(`importance: BLOCK`)で確認を取る。
