所属フェーズ: 4(思いつく改善すべて)。人間の確認は不要な修理として登録する。

## 症状

ccloop がタスクごとに作る作業場所(git worktree のディレクトリ)を、人間が
`git worktree remove` を経由せずファイルごと削除すると、git のリポジトリ側には
「このブランチはそこで使用中」という管理情報が残る。この状態で同じタスクが再び選ばれると
作業場所の作成が git に拒否され、セッションは起動できずに失敗する。

失敗するとやり直し回数が 1 つ減るが、原因は解消されないため次の試行もまったく同じ理由で失敗し、
やり直し上限に達してタスクが `failed` になる。タスクの中身とは無関係な理由でやり直し回数が
尽きる点で、`T-20260830-0621-conflict-retry-always-reconflicts` と同じ系統の問題である。

## 原因(調査済み)

古い管理情報を掃除する `pruneWorktrees()` は `ccloop run` のプロセス起動時
(`lib/supervisor.ts` の起動時復旧)からしか呼ばれない。タスクごとの作業場所作成は
`lib/hooks/worktree-create.ts` → `lib/worktree.ts` の `createWorktree()` を通るが、
この経路に掃除は入っていない。そのため `ccloop run` を再起動しない限り自己回復しない。

`createWorktree()` は「ディレクトリが無い / ブランチはある」という分岐で
`git worktree add <path> <branch>` を実行する(`lib/worktree.ts:109-117` 付近)。

確認済みの事実: 上記の呼び出し関係と分岐はコード読解で確認済み。
未検証の推測: 「管理情報が残った状態で `git worktree add` が実際に拒否される」ことは
git の既知の挙動として高確度だが、調査時の権限制約(`Bash(git worktree*)` が禁止)により
実機では再現していない。着手時にまず一時リポジトリで再現を取ること。

## 完了条件

- 作業場所の作成前にも古い管理情報の掃除が行われ、人が作業場所を直接消しても
  次の試行が正常に起動できる
- 上記の再現(管理情報だけ残った状態からの復帰)を確かめるテストがある
- typecheck / lint / test が通る

## 注意

掃除は他のタスクが使用中の作業場所を巻き込まないこと(`git worktree prune` は
実在するディレクトリの記録には触れないが、実装方法を変える場合は要確認)。
