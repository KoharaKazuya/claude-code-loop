(`HR-20260830-1053-topic-conflict-prone-parallelism`)。

## 背景(なぜやるか)

ccloop は最大 4 件のタスクを並列に走らせるが、このリポジトリの本体は `lib/supervisor.ts` に
集中しているため、並列セッションがほぼ確実に同じファイルを編集する。結果、マージ衝突で
失敗扱いになったタスクがこれまでに 4 件出ており、うち 3 件は完成した成果が退避ブランチに
取り残されて救出作業が必要になった。

応急処置として、探索セッションが衝突しそうなタスク同士に `dependencies` を手で張って直列化して
きた(`D-20260830-1053-serialize-supervisor-hotspot-tasks`)。これは張り忘れると元に戻る。

人間の回答(`HR-20260830-1053-topic-conflict-prone-parallelism`)は次のとおり:

> 探索セッションが競合しそうなタスクを判断し、タスクに(依存と同じようにして)競合のメタデータを
> 持たせるようにして、タスク選択時に競合を同時に実行しないようにしたい

つまり **`dependencies` と並ぶ新しい frontmatter フィールドとして「競合」を持たせ、
タスク選択のときに競合するタスクを同時に走らせない**、という方針が採用された。
このタスクはその**ツール側の仕組み**(フィールドの読み書きと選択ロジック)を実装する。
探索セッションに競合を判断させる指示の追加は別タスク
(`T-20260830-1334-explore-assigns-conflict-metadata`)で行う。

## やること

1. タスク frontmatter に `conflicts: [<タスク ID>, ...]` を追加する。
   - 型定義とパースは `dependencies` と同じ場所に並べる(`lib/supervisor.ts:162` の型、
     `:326` の許可キー一覧、`:348` のパース、`:537` のシリアライズ相当)。
   - 未指定は空配列として扱い、既存のタスクファイルがそのまま読めること(後方互換)。
2. タスク選択で、**実行中のタスクと競合するタスクを選ばない**ようにする。
   - 競合は対称に扱う。A の `conflicts` に B が書かれていれば、B 側に記載が無くても
     A と B は同時に走らない。
   - 同じ周回で複数件を新たに起動する場合、**その周回で選んだもの同士**も競合しないようにする
     (実行中との比較だけでは足りない)。
   - 実行中が 0 件なら必ず 1 件は選べるので飢餓は起きない。この性質をテストで固定する。
   - 存在しない ID が `conflicts` に書かれていたときの扱いを決める(`dependencies` は
     `lib/supervisor.ts:2122` 付近で欠落を検出している)。**競合は「同時に走らせない」だけの
     ヒントであり、欠落しても停止させる理由が無い**ため無視する方向を推奨するが、実装時に
     判断して理由を `.agent/decisions/` に記録すること。
   - 依存の輪(`lib/supervisor.ts:6011` 付近)のような**デッドロックが起きない**ことを確認する。
     競合は「今は選ばない」だけで待ち続ける関係ではないので輪にならないはずだが、テストで示す。
3. `ccloop status` で、競合のせいで起動を見送られたタスクがあることが分かるようにする
   (次に実行予定の一覧で理由が読めれば十分。表示を増やしすぎないこと)。
4. `ccloop add` に競合を指定する手段を用意するかどうかを判断する。`--deps` に相当する
   `--conflicts` を足すのが自然だが、探索セッションはファイルを直接書くので必須ではない。
   足さない判断をした場合はその理由を `.agent/decisions/` に残す。
5. テストを足す(`lib/scheduler.test.ts` / supervisor 系のテストのうち適切な場所)。
   最低限、次を固定する: 競合するタスクが同時に選ばれないこと / 実行中が 0 件なら選べること /
   同一周回で複数起動するときも競合しないこと / `conflicts` 未指定の既存タスクが読めること。
6. `CHANGELOG.md` の「## 未リリース」節に利用者の言葉で 1 行足す。
7. `docs/` に、競合メタデータの目的(並列実行の衝突を減らす)と `dependencies` との違い
   (依存は順序、競合は同時実行の排除)を短く記す。コードから自明な事実は書かない。

## 完了条件

- `conflicts` を書いたタスク同士が同時に起動されないことがテストで固定されている。
- 既存のタスクファイル(`conflicts` 無し)の挙動が変わっていない。
- 機械的検証(`npm test` / lint / typecheck)が通る。

## 注意

- `lib/supervisor.ts` は並列セッションのホットスポットである。このタスクは**そこを大きく触る**ので、
  同時に他のタスクが `lib/supervisor.ts` を編集していると衝突する。`dependencies` で
  直列化してあるが、着手時に他の実行中タスクが同じファイルを触っていないか確認すること。
- 変更範囲を広げないこと。巨大ファイルの分割は今回の対象外(人間は分割ではなく仕組みの追加を選んだ)。
