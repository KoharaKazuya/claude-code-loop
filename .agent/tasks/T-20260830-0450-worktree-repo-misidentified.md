所属フェーズ: 4(思いつく改善すべて)。ただし本件は「壊れているものの修理」に当たるため、
個別の確認 HR は不要と判断して直接タスク化している(判断の物差しは `.claude/CLAUDE.md` の
変更履歴の運用ルールに従う)。

## 目的

ccloop 自身が作った git worktree のディレクトリの中でコマンド(`ccloop status` など)を実行すると、
同じリポジトリであるにもかかわらず**別リポジトリとして扱われ、無関係な(多くの場合は空の)
実行状態を参照してしまう**。この誤認を解消する。

## 現状(調査で確認済みの事実)

- `lib/paths.ts` の `findGitRoot`(52-60 行目付近)は `.git` がディレクトリでもファイルでも
  ルートとみなす。git worktree では `.git` はファイルなので、worktree のディレクトリ自身が
  ルートとして確定する。
- `repoId`(109-113 行目付近)は `realpath` した**パス文字列**の sha1 から ID を作るため、
  worktree のパスは本体リポジトリとは別の ID になり、`stateDirFor` が指す状態ディレクトリ
  (`state.json` / `metrics.jsonl` / パッチ退避先)も別物になる。
- `.agent/` は git 管理下なので worktree 側にもチェックアウトされている。そのため
  `.agent/config.json` も `GOAL.md` も存在し、**一見正常に動いているように見える**のが厄介な点。
- `resolveRepoRoot` は `--repo` / `CCLOOP_REPO` を最優先する。Supervisor は子セッションへ
  `CCLOOP_REPO`(本体のパス)を渡している(`lib/supervisor.ts:1800` 付近)ため、
  **自律セッション自身は影響を受けない**。影響を受けるのは、人間が素のシェルで worktree の
  ディレクトリに入って ccloop を実行した場合である。
- 衝突で退避された worktree は削除されずに残り `ccloop status` がその存在を知らせる作りなので、
  人間がその worktree に入って調べる導線は実際に存在する。この経路で誤った状態を見せるのが
  実害として最も現実的である。

## やること

1. 解決したリポジトリのルートが**リンクされた worktree** であるとき、本体のワークツリーへ
   読み替えるようにする。`.git` がファイルの場合その中身は `gitdir: <本体>/.git/worktrees/<名前>`
   の形なので、git のサブプロセスを起動せずにファイルの内容から本体のパスを導ける
   (現在の `resolveRepoRoot` が git を起動しない純粋な実装であることを崩さないため、
   この方針を優先する。`.git` ファイルの書式が想定外だった場合は現在の挙動へフォールバックし、
   例外で落とさないこと)。
2. `--repo` / `CCLOOP_REPO` で worktree のパスを渡された場合も同じ読み替えを適用する
   (指定を黙って別リポジトリへすり替えるのとは異なり、同一リポジトリの本体を指すだけなので
   `resolveRepoRoot` の既存コメントにある「意図しない場所を書き換える」懸念には当たらない)。
3. 既存の挙動を壊さないこと。特に、本体リポジトリのルートを渡したときの `repoId` が
   変わらないこと(変わると既存利用者の状態ディレクトリが行方不明になる)。

## 完了条件

- `lib/paths.test.ts` に次を確認するテストを追加し、通ること。
  - 実際に `git worktree add` で作った worktree の中から解決したルートが本体と一致し、
    `repoId` も本体と同じになる。
  - 本体リポジトリのルートを渡したときの `repoId` が従来と変わらない。
  - `.git` ファイルの中身が想定外の形式でも例外にならず、従来どおりそのディレクトリを返す。
- `npm run` 経由で利用可能な機械的検証(tests / lint / typecheck / build のうち該当するもの)が通ること。
- 利用者から見た挙動が変わるため、`CHANGELOG.md` の「## 未リリース」節に 1 行追加すること
  (同じコミットに含める)。
- コードから読み取りづらい背景ではないため docs/ への追記は不要。必要と判断した場合のみ最小限に留める。

## 範囲外

- 同一リポジトリでのループ二重起動の防止(別タスク `T-20260830-0443-double-run-guard` の担当)。
- bind mount など、realpath で解決されない別マウント経由の同一実体パスの扱い。発生条件が
  限定的で未検証のため、本タスクでは扱わない。
