## 経緯

`HR-20260830-0303-topic-changelog-release-notes`(BLOCK)で「変更履歴のファイルを作って、
以後セッションが更新していく運用にしてよいか」を確認し、人間から「作る」と回答を得た。
このタスクはその 1 段目(ファイルの新規作成と過去分の遡及まとめ)を担当する。
以後の更新運用のルール化は `T-20260830-0341-changelog-update-rule` が担当する。

## 目的

「いまの公開版に何が入っていて、何が入っていないか」を、コミット履歴を自分でたどらずに
読み取れるようにする。

## やること

1. リポジトリ直下に変更履歴ファイル(`CHANGELOG.md`)を 1 つ作る。
2. 公開済みの各バージョン(最新の公開版は 0.4.1)に何が入ったかを、Git のタグ・コミット履歴から
   さかのぼってまとめる。
3. 公開版 0.4.1 より後の未公開コミットを「未リリース」節としてまとめる。件数は日々増えるので、
   着手時点の `git log` から実際の範囲を確認すること。この中には決定へのチェックによる承認の
   仕組み、`ccloop status` の承認待ち件数表示などが含まれる。
4. `README.md` から `CHANGELOG.md` へたどり着けるようにリンクを置く。

## 書き方の方針

- **読者はエージェントではなく人間の利用者**である。内部の関数名・ファイルパス・タスク ID を
  並べず、「利用者から見て何ができるようになったか / 何が直ったか」を 1 行で書く。
- 粒度は `.agent/decisions/D-20260830-0303-phase4-consent-granularity.md` が定める
  「リリースノートに 1 行として載る粒度」に揃える。内部テストの追加や内部文字列の整合など、
  利用者から見て何も変わらない変更は載せない。
- バージョンの並びは新しいものが上。各版に日付を添える。
- 過去分は commit を 1 対 1 で写さない。同じトピックの複数コミットは 1 行にまとめる。

## 完了条件

- `CHANGELOG.md` が存在し、公開済み各版と未リリース分が上記の方針で書かれている。
- `README.md` からリンクされている。
- `npm run` 経由の lint / typecheck / test が通る(このタスクはドキュメント追加のみのため
  影響しないはずだが、既存の検証が壊れていないことは確認する)。

## やらないこと

実際にバージョンを上げて公開する操作(`npm run release`)は行わない。これは人間が実行する。
`package.json` / `devcontainer-feature.json` のバージョン番号も変更しない。
