所属フェーズ: 4(思いつく改善すべて)。壊れているものの修理なので人間への確認は取らずに進めてよい。

## 何が起きているか

このリポジトリ本体に、テスト用の作り物としか思えない名前のブランチが存在する。

```
T-001         2026-08-30 06:19:08
agent/T-001   2026-08-30 03:05:10
agent/T-002   2026-08-30 03:05:10
agent/T-003   2026-08-30 03:05:10
agent/T-999   2026-08-30 03:05:10
```

`T-001` / `T-999` は `lib/merge.test.ts` と `lib/supervisor.test.ts` が使うタスク ID である
(`grep -rln "T-999" --include=*.ts lib/` で確認済み)。これらのブランチは**実際の main の
コミット**(`4d3d614` / `859dff6` / `a9f32aa`)を指しており、使い捨ての一時リポジトリではなく
**このリポジトリ本体に作られた**ことが分かる。作られた時刻が 03:05 と 06:19 の 2 回に
分かれていることから、一度きりの事故ではなく繰り返し起きている。

## なぜ問題か

1. **開発者のリポジトリが汚れる。** テストを走らせるたびにブランチが増え、誰も消さない。
2. **ccloop 自身の回収処理と紛らわしい。** 起動時の孤児ブランチ回収は `refs/heads/agent/*` を
   起点にしており、`agent/T-001` などはその条件に一致する。対応するタスクファイルが無いため
   警告に落ちて実害は出ていないと見られるが(`.agent/OVERVIEW.md` の突き合わせ記録)、
   **テストの残骸と本物の作業ブランチが同じ名前空間に同居している**状態そのものが危うい。
   条件がわずかに変われば、テストの残骸を本物の成果と誤認して main へ統合しようとしうる。
3. テストが実リポジトリの状態に依存・干渉するため、テスト結果が実行環境の履歴に左右される。

## やること

1. どのテストが実リポジトリにブランチを作っているかを特定する。`lib/merge.test.ts` /
   `lib/supervisor.test.ts` から見ていくのが早い。**一時ディレクトリに使い捨てリポジトリを
   作る想定だったのに、実行時の作業ディレクトリ(= 本体)に対して git を叩いている経路**を疑う。
2. その経路を直し、テストが本体リポジトリを一切変更しないようにする。
3. **同じ事故を再発時に検出できるようにする。** 例えばテスト実行の前後でブランチ一覧が
   変わっていないことを確かめる。ここまでやらないと、また静かに戻る。
4. 残っている残骸ブランチ(`T-001` / `agent/T-001` / `agent/T-002` / `agent/T-003` /
   `agent/T-999`)の削除は**セッションの権限外**である。削除してよい根拠(テストの残骸であり
   固有の成果を含まないこと)を確認したうえで、`.agent/human-review/` に人間へ削除を依頼する
   エントリを 1 件作る。中身を確認せずに「消してよい」と書かないこと。

## 完了条件

テストを実行しても本体リポジトリのブランチ一覧が変わらないこと。その保証が自動で確かめられること。
機械的検証が通ること。

## 注意

調査で `git worktree` 系のコマンドは権限で使えない。ブランチの作成・削除・切り替えも同様に
使えないため、再現はテストコードの読解と、テスト自身が用意する一時リポジトリの中で行うこと。
