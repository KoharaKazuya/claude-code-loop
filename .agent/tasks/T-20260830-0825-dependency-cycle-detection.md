`HR-20260830-0621-topic-dependency-cycle` で取得済み(「やる」)。ただし確認時に
**優先度は低い**と伝えたうえでの同意なので、他の修理より後でよい。

## 何が起きているか

タスクどうしの依存関係が輪になっている(A は B の完了待ち、B は A の完了待ち)と、
どちらも「依存が全て完了した」条件を満たせず、次に実行するタスクの候補に一生入らない。
依存が失敗・ブロック済みかどうかを見る判定も、輪の場合はどちらも「失敗」ではないため反応しない
(タスク選定は `lib/supervisor.ts`。関数名で当たりを付けてから読むこと)。

エラーにも警告にもならず、`ccloop status` 上は依存の完了を待っている「実行できる状態」に
見えたまま止まり続ける。巻き込まれるのは輪に加わったタスクだけでループ全体は止まらないが、
**なぜそのタスクだけがいつまでも始まらないのか人間には分からない。**

## やること

1. 依存の輪を検出する。自己参照(自分自身を依存に書く)も輪として扱う。
2. 検出したら `ccloop status` の「要対応」の一覧に出す。**輪に加わっているタスクの ID が
   すべて分かる**形にする(人間はどれか 1 本の依存を消せば解けるので、輪の構成が見えることが
   そのまま解決手順になる)。
3. 表示は「人間が直せる」形にする。内部用語ではなく、何が起きていてどうすれば解けるかが
   伝わる文言にする。
4. 輪がある場合・ない場合・自己参照・輪が複数ある場合を確かめるテストを足す。
5. 利用者から見た表示が変わるので `CHANGELOG.md` の「## 未リリース」に 1 行足す。

## やらないこと

- 輪の自動解消(依存を勝手に消す)。人間が書いた指定を機械が黙って書き換えるのは、
  このループが避けている方向である。検出して見せるところまでにする。
- 存在しないタスク ID を依存に書いた場合の扱い。これは別タスク
  `T-20260830-0808-missing-dependency-silently-ignored` が扱う。**同じ依存解決の処理を触るので、
  そちらが先に入っていれば衝突を避けるため後から統合すること。**

## 完了条件

依存が輪になったタスクが `ccloop status` の「要対応」に構成タスク ID 付きで出ること。
機械的検証が通ること。
