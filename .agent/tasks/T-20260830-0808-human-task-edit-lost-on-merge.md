所属フェーズ: 4(思いつく改善すべて)。人間の確認は不要な修理として登録する。

## 症状

あるタスクをセッションが実行している最中に、人間が main 側で同じタスクのファイル
(`.agent/tasks/<ID>.md` の priority や note など)を手で編集する。
セッション終了時のマージでその箇所が衝突すると、自動解消はタスクファイルを常にブランチ側の
内容で採用するため、人間の編集は解消結果にも記録にも残らず、警告も出ない。

`.agent/` は人間が自由に編集してよい場所として案内しているので、編集が黙って消えるのは
その前提と食い違う。

## 原因(調査済み)

`lib/merge.ts` の `classifyConflicts` / `resolveMechanically` は、衝突したパスが
自タスクのファイルと `.agent/decisions/index.md` だけなら機械的に解消してよいと判断し、
自タスクのファイルは `git checkout --theirs`(ブランチ側)で確定する
(`lib/merge.ts:86` / `196` / `306-316` 付近)。

この設計は「main 側の変更は ccloop 自身が書いた機械的な失敗記録に過ぎない」という前提に
立っている(`docs/architecture.md` および `D-20260830-0544-task-file-conflict-match-main`)。
人間が同じファイルを直接編集する場合は想定に入っていない。

確認済みの事実: 上記の分岐と設計上の前提はコード読解・既存テスト・docs で確認済み。
未検証の推測: 実機での再現(実際に人間の編集と衝突させる)は未実施。行単位で衝突しない編集
(別の項目だけを変えた場合など)は git が両方残すため、常に起きるわけではない。

## 依存の理由

`T-20260830-0621-conflict-retry-always-reconflicts` が同じ自動解消の仕組みに手を入れている。
そちらが main に入ってから着手すること(同じ箇所を並行して変更すると衝突する)。

## 完了条件

- 人間の編集が黙って失われないこと。捨てる内容がある場合は、捨てた事実と捨てた内容が
  人間の目に触れる場所(解消コミットのメッセージ、`ccloop status` の要対応、
  タスクの試行履歴のいずれか)に残る
- ブランチ側を採用する既存の方針そのものを変える必要は無い。「静かに捨てる」のをやめるのが目的
- 「main 側の変更が ccloop の機械記録か人間の編集か」を見分ける方法は実装時に判断し、
  `.agent/decisions/` に記録する(コミットの著者で見分ける、あるいは見分けずに常に
  捨てた内容を残す、など)
- テストがある。typecheck / lint / test が通る
