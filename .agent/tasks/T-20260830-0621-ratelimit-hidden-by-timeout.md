所属フェーズ: 4(思いつく改善すべて)。壊れているものの修理なので人間への確認は取らずに進めてよい。

## 何が起きているか

セッション終了時の分類(`finishTaskSession`、`lib/supervisor.ts:3143-3150` 付近)は
**時間切れを最優先で見る**。

```
if (res.timedOut) {          // ← 先に来る
  fail("タイムアウト(...)", "timeout");
} else if (rateLimited) {
  applyRateLimit(config);
}
```

一方、利用上限の判定(`lib/ratelimit.ts` の `detectRateLimit`)は、終了コードが 0 以外なら
出力の文言で判定する設計である。**「利用上限に当たったが CLI がすぐには終了せず、40 分の
時間切れで打ち切られた」**場合、出力に上限の文言が含まれていても時間切れとして分類され、
利用上限の分岐に入らない。

`detectRateLimit` が終了コードを問わず文言で判定しているのは、「上限に当たっても CLI が
すぐに終了しないことがある」という前提があるからである。その前提が成り立つ状況で、
まさにこの取りこぼしが起きる。

## 実害

1. **やり直し回数が消費される。** 「利用上限は `retries` を消費しない」という設計が破られる。
2. **待機が入らない。** 待機時刻が更新されないので、次の周回ですぐ新しいセッションを起動する。
   上限が解除されていなければ同じことを繰り返す(40 分のセッションを無駄撃ちし続ける)。
3. **モデルが昇格して費用が増える。** `retries` が昇格のしきい値(既定 2)に達すると
   `pickModel`(`lib/supervisor.ts:2696-2699` 付近)がより高価なモデルへ切り替える。
   原因は利用上限なのに、難しいタスクとみなして費用を上げてしまう。
4. 3 回重なるとタスクが `failed` になる。中身に問題が無いのに失敗が確定する。

## 実際に確かめたこと

一時リポジトリで `finishTaskSession` を
`{ exitCode: null, timedOut: true, stdout: "Claude AI usage limit reached...", stderr: "" }`
で直接呼び、次を確認済み:

- `retries` が 1 に増える
- `note` が「失敗のため ready に戻す(1/3)。理由: タイムアウト(2400000ms)」になる
- 待機状態が `{"resumeAt":null}` のまま(待機が一切設定されない)

なお「利用上限で CLI が時間切れまで居座る」ことが実際に起きるかは未検証である
(CLI 側の挙動はこのリポジトリからは確認できない)。ただし判定側の設計がその可能性を
前提にしている以上、取りこぼしは塞いでおくべきである。

## 参考(同じ重なりを既に考慮している箇所がある)

crash-backoff のストリーク管理(`nextFastCrashStreak`、`lib/supervisor.ts:920-922` 付近)は
「時間切れかつ利用上限」の重なりを明示的に考慮し、テストもある
(`lib/supervisor.test.ts:2342-2343` 付近)。`finishTaskSession` の側だけがその考慮を
持っていない、という非対称になっている。直すときはこの既存の扱いと整合させること。

## やること

1. 分類の順序または条件を見直し、**時間切れであっても利用上限と判定できるならそちらを優先**する
   ようにする。判定順序には意味があるとコメントにあるので、なぜその順序なのかを読んでから
   変えること。他の分岐(マージ結果など)への影響も確認する。
2. 変更後も「時間切れは 3 回で失敗になる」安全網が壊れないこと。利用上限として扱う条件を
   広げすぎると、本物の時間切れが失敗として数えられなくなる。線引きの根拠を
   `.agent/decisions/` に記録すること。
3. テストを足す(時間切れかつ出力に利用上限の文言があるとき、`retries` が増えず待機が入ること)。
4. 利用者から見た挙動が変わるので `CHANGELOG.md` の「## 未リリース」に 1 行足す。

## 完了条件

利用上限が時間切れに隠れた場合でも、やり直し回数を消費せず待機が入ること。機械的検証が通ること。
