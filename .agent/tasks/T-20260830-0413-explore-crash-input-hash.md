## 目的

探索セッションが異常終了しても、GOAL の変更や Human Review の回答を「確認済み」として
記録してしまう経路を塞ぐ。放置すると、人間が書いた入力が読まれないまま黙って捨てられる。

## 現状

`runExploreSession`(`lib/supervisor.ts`、`state.inputsHash` を更新している箇所)は、
レートリミット以外で終わったセッションについて `exitCode` を見ずに
`inputsHash` / `goalHash` / `answeredKeys` を更新している。レートリミットの場合だけは
「復帰後に再度取り込ませる」ために更新をスキップする作りになっており、異常終了は考慮外に
見える。

この結果、次の経路が成立する。

1. 人間が GOAL.md を編集(または Human Review に回答)して `ccloop run` を実行する
2. 探索セッションが起動直後にクラッシュする(例: claude コマンドの設定ミス)
3. 入力ハッシュだけが「確認済み」として更新される
4. 次周回は `inputsDirty` が false になり探索条件が成立せず、ループは idle-exit する
5. 以降の `ccloop run` も同じ入力ハッシュのままなので、即座に「やることが無い」と判断して
   終了し続ける。人間の入力は取り込まれないまま失われる

異常終了には「起動直後のクラッシュ」と「締め切りによるタイムアウト(実際には作業済み)」の
両方が含まれる点に注意する。後者まで一律に未消費扱いにすると、取り込み済みの入力を毎回
読み直させることになりうる。切り分け方(exitCode だけで判断するか、瞬時クラッシュ相当の
壁時計時間も見るか)を決めることがこのタスクの設計上の主眼である。

## 完了条件

- 異常終了した探索セッションが人間の入力を消費しないこと。切り分けの基準と、その基準を
  選んだ理由を `.agent/decisions/` に記録する
- 入力を未消費のままにする変更は、探索の再起動条件(`inputsDirty`)を成立させ続けるため、
  瞬時クラッシュが続くと探索の即時再試行が連鎖しうる。空回りを防ぐ歯止めを併せて設計する
  (関連する既存判断: `.agent/decisions/D-20260830-0410-explore-crash-out-of-scope.md`)
- 上記の分岐を検証する回帰テストを追加する
- `npm run` 経由の test / typecheck / lint が通ること

## 制約

`ccloop run` の停止条件(いつループを諦めるか)は利用者から見た挙動である。既存の
crash-backoff の閾値・停止条件そのものを変える必要が出たと判断した場合は実装せず、判断を
`.agent/decisions/` に記録したうえでこのタスクを `blocked` にし、`.agent/human-review/`
(`importance: BLOCK`)で確認を取る。
