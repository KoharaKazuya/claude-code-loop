所属フェーズ: 4(思いつく改善すべて)。人間の同意は
`HR-20260830-0621-topic-status-grows-slow` で取得済み(「読む量に上限を設けて」)。

## 何が起きているか

`ccloop status` と `ccloop watch` は、実行のたびに追記される計測ログ(所要時間・費用)と
権限拒否の記録を**毎回全件読んで集計している**(`lib/supervisor.ts` の `loadMetrics` /
`loadPermissionDenials`)。記録は上限なく貯め続ける方針がコード内のコメントで明示されている。
`ccloop watch` は既定で 1 秒ごとに読み直すため、使い込んだリポジトリほど表示が重くなる。

## やること

1. 読み込み量に上限を設ける(ファイル末尾から直近ぶんだけ読む、など)。上限の値は
   「実用上まず困らない量」を根拠とともに決め、`.agent/decisions/` に記録する。
2. **集計値の意味が変わる点を利用者に隠さない。** 上限にかかったとき、費用などの合計が
   「全期間」ではなく「直近ぶん」であることが表示から分かるようにする(例: 対象範囲を添える)。
   人間はこの点を承知のうえで同意しているが、数字の意味が黙って変わるのは避ける。
3. 上限にかかる規模の記録を作って、読み込みが打ち切られること・表示が壊れないことを
   確かめるテストを足す。
4. 利用者から見た挙動が変わるので `CHANGELOG.md` の「## 未リリース」に 1 行足す。

## やらないこと

- 古い記録の削除・圧縮。読む量を絞れば目的は足りる。記録そのものは残す
  (後から人間が生ファイルを読める価値がある)。
- 集計結果のキャッシュ(次回のために持ち回る)。実装が複雑になるわりに、読む量の上限だけで
  効果が出るなら不要。上限だけでは足りないと分かった場合にのみ別タスクとして検討する。

## 完了条件

記録が大量にあっても `ccloop status` / `ccloop watch` の読み込み量が一定に収まり、
集計値の対象範囲が表示から分かること。機械的検証が通ること。
