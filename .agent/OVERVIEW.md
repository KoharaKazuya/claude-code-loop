## 確認トピックの在庫(枠が空き次第そのまま HR にすればよい)

調査済みで根拠も揃っているが、確認枠が満杯のためまだ人間に投げていないもの。
いずれも「壊れている」のではなく仕様の選択なので、修理として勝手に進めないこと。

1. **記録が増え続けると状況表示が重くなる件**。`metrics.jsonl` / `permission-denials.jsonl` と
   `.agent/archive/tasks/` を、`ccloop status` と `ccloop watch` が毎回**全件**読んで集計している
   (`lib/supervisor.ts` の `loadMetrics` / `loadPermissionDenials` / `loadArchivedTasks`)。
   `watch` は既定 1 秒間隔なので、長く使うほどじわじわ遅くなる。無制限運用はコード内のコメントで
   明示された当初の選択であり、覆すなら確認が要る。
2. **複数のリポジトリで同時にループを回すと、利用上限の待機が共有されない件**。待機の状態は
   リポジトリごとの状態ディレクトリに保存されるが、実際の利用上限はアカウント単位で課される。
   片方が待機に入っても、もう片方は上限中のままセッションを起動し続ける。
3. **ループが致命的な理由で自分から止まっても `ccloop status` に何も残らない件**。リポジトリ本体が
   git 操作の途中で固まり自己修復にも失敗すると、`ccloop run` は「対処後に再起動すること」と
   ログして止まる(`lib/supervisor.ts:3355-3366`)。この文言は画面に出るだけで永続化されず、
   終了時の後始末が生存記録を消す(同 `3582-3596`)ため、以後 `ccloop status` は「一度も起動して
   いない」場合と全く同じ文言しか出さない(`lib/liveness.ts:292-299`)。要対応セクションにも
   本体の固まりを検知する項目が無い(`collectPendingConflicts` は衝突ブランチとタスク worktree
   のみを見る)。**直す方向自体に議論の余地は薄いが、「起動していません」の文言をどう区別するか・
   要対応に何を足すかは表示の設計判断**なので確認が要る。次に枠が空いたらこれを最優先で出すこと。
4. (優先度低)**タスクの依存が循環していると、無警告のまま `ready` で永久に選ばれない件**。
   クラッシュも全体停止もせず、巻き込まれるのは循環に加わったタスクだけ(`planTaskSelection` を
   直接呼んで確認済み)。検出・警告を足すかは設計判断。実害が小さいので在庫の中でも後回しでよい。
5. (優先度低)**走行中タスクの記録ファイルを探索セッションが編集しない保証が、プロンプトの
   指示だけである件**。コード側の強制は無い(`lib/supervisor.ts:2574-2589` が一覧を注入するのみ。
   `lib/hooks/stop-check.ts:24` は探索セッションでは何も検査せず即終了する)。違反した場合でも
   同じ行なら 3-way マージが衝突として検出して安全に止まるため、実害は「別々の行の編集が
   レビューされないまま静かに混ざる」程度にとどまる。強制を足すかは設計判断であり、
   在庫の中では最も後回しでよい。
