タスク frontmatter に `conflicts: [<タスクID>, ...]`(同時に実行しないタスク)を追加するにあたり、
仕様の細部を次のように決めた。

## 存在しない ID は黙って無視する

`dependencies` は欠落を `ccloop status` の要対応として検出する(依存先が無ければ「いつ実行して
よいか」が決まらず、タスクが永久に待つため)。`conflicts` は「同時に走らせない」だけのヒントで
あり、相手が居なければ制約が無いのと同じで、誰も待たない。止める理由が無いので検出も警告もしない。

ただし `ccloop add --conflicts` では ID の存在を検証して弾く。これは人間の打ち間違いを入力時に
拾うためで、実行時に欠落を許すこととは役割が違う(タスクが archive へ退役したあとも、残った
`conflicts` の記述で失敗させたくない)。

## 関係は対称に扱う

A の `conflicts` に B が書いてあれば、B 側に記載が無くても A と B は同時に走らない。片側だけ書けば
足りるので、探索セッションが 2 ファイルを同時に整合させる必要がなくなる(片側の書き忘れが
そのまま制約の消失になるのは事故りやすい)。

## 空配列のときは frontmatter に書き出さない

`dependencies` は常に書き出されるが、`conflicts` は空なら省略する(`conflictRetries` と同じ扱い)。
常に書き出すと、既存の全タスクファイルが次の保存時に `conflicts: []` の 1 行を増やすだけの差分を
生み、Git 履歴のノイズになる。読み込み側は未指定を空配列として扱うため挙動は変わらない。

## 選択は優先度順の貪欲法(飢餓もデッドロックもしない)

`planTaskSelection` が実行中のタスク ID を占有済みとして持ち、優先度順に候補を見て、占有済みと
競合するものを `conflictHeld` へ落とす。選んだものは占有済みに加えるので、同じ周回で複数起動する
場合も互いに競合しない。実行中が 0 件なら占有済みが空なので先頭候補は必ず残る(飢餓しない)。
競合は「今は選ばない」だけで相手の完了を待ち続ける関係ではないため、輪になってもデッドロックしない。

この結果 `runnable` は「実行中とも互いにも競合しない」列になるので、`lib/scheduler.ts` 側は
先頭から空き枠数だけ取る従来のままでよく、ロジックを変更していない。

## 名前について

英語の "conflict" と日本語の「衝突」は、このリポジトリでは既に Git のマージ衝突を指す語として
広く使われている。それでも frontmatter のフィールド名は `conflicts` にした。人間が
`HR-20260830-1053-topic-conflict-prone-parallelism` で「競合のメタデータ」と表現しており、
利用者から見て最も素直な名前であるため。コード内でマージ衝突と紛らわしくなる箇所は識別子で
書き分ける。
