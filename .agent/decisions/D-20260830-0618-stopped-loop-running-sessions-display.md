## 判断内容

`runningSessionLines` に `LoopLiveness` を必須引数として渡し、ループ本体の死活で表示を 3 分岐する。

- `running`: 従来どおり(見出し `実行中のセッション (n/max)`、経過時間、タイムアウト超過の注記)
- `stopped`(`no-record` / `process-gone`): 経過時間とタイムアウト注記を出さない。代わりに
  `※ ループ本体(ccloop run)が動いていないため、下記の N 件は実行中ではなく記録が残っているだけ`
  の 1 行と、各セッションの `<startedAt> 開始(ループ停止時のまま残った記録)` を出す。
  `formatStatus` 側の節見出しも `実行中のタスク(ループ停止時の記録)` に変える
- `unknown`(`heartbeat-stale` / `foreign-host` / `record-unreadable`): 従来の表示のまま、
  `※ ループ本体(ccloop run)の生存を確認できないため、下記は古い記録の可能性がある` を 1 行足す

## 理由

- **経過時間を止めたのが本質**。`ccloop watch` は毎フレーム `now - startedAt` を再計算するため、
  ループが死んでいても数字が 1 秒ごとに増え、「動いている感」だけが強まっていた。警告を添える
  だけでは、増え続ける数字が警告文より強く「動いている」と主張してしまう
- タイムアウト超過の注記(`※ タイムアウト(40分)を超過 — supervisor が停止していれば古い表示`)は
  「停止しているかもしれない」という推測の注記であり、停止が確定している場面では冗長かつ弱い。
  確定情報で置き換える
- `unknown` で断定しないのは、`foreign-host`(別マシンの状態を見ている)が正常運用でも起きうるため。
  ここで「実行中ではない」と断定すると逆向きの誤情報になる

## 検討した代替案

- **警告行を添えるだけ(経過時間は維持)**: 実装は最小だが watch の数字が増え続ける問題が残る。不採用
- **stopped のときセッションを非表示にする**: 矛盾は消えるが、どのタスクが中断されたかという
  再起動判断に必要な情報まで失われる。不採用
- **`state.json` の `runningSessions` を status 実行時に掃除する**: 表示ではなく状態を直す案。
  読み取りコマンドが状態を書き換えるのは副作用が大きく、`unknown` では掃除の可否を判断できない。不採用

## 影響範囲

- `runningSessionLines` の呼び出しは `formatStatus` の 1 箇所のみ。`ccloop watch` も
  `formatStatus` を再利用しているため同時に直る
- `--json` 出力は変更していない。`loopLiveness` が既に含まれており、消費側は
  `runningSessions` と突き合わせて自前で判定できるため
