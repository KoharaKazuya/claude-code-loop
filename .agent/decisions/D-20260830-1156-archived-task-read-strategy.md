## 判断

`.agent/archive/tasks/` の完了済みタスクを `ccloop status` / `ccloop watch` が読むとき、
全文読み(`loadArchivedTasks`)をやめ、次の 2 段で読む(`loadArchivedTaskSummaries`)。

1. 各ファイルの先頭 4 KiB だけを読んで frontmatter を取り出す(`readFrontmatterData`)。
   閉じ `---` がその範囲に収まらない異例のケースだけ全文を読み直す。
2. 絶対パス → (mtimeMs, size, summary) のプロセス内キャッシュを持ち、
   mtime と size が変わっていないファイルは再パースしない。

## 理由

- 進捗集計と依存表示が archive のタスクから使うのは `id` と `status` だけで、本文(試行履歴が
  積み上がって数 KB になる)は一切使っていない。読む量を落としても**進捗の完了数・総数は
  1 件も変わらない**。これがタスクの最優先要件だった。
- `ccloop watch` は同一プロセスで毎秒 `formatStatus()` を呼び直す。archive のタスクは片付けで
  移された後ほぼ不変なので、プロセス内キャッシュが最も効く場所がここになる。

## 検討した代替案

- **完了数を別ファイルに持つ(カウンタ)**: 読む量は最小になるが、実体ファイルとカウンタが
  ずれたときに進捗の数字が静かに狂う。数字の正確さを最優先する要件と噛み合わないので採らない。
- **読む件数に上限を設ける**: 計測ログ(`T-20260830-0825-metrics-read-cap`)ではこれを採ったが、
  タスクの進捗は「累積の実績」なので直近ぶんに置き換わると意味を失う。採らない。
- **集計結果をディスクへ永続キャッシュ**: 無効化の設計が要るわりに、部分読み + プロセス内
  キャッシュで足りる。必要になってから検討する。

## 影響範囲

- `lib/supervisor.ts` の `collectStatusData` と `cmdList`。表示は変わらない。
- キャッシュは mtime と size の両方が一致したときだけ再利用する。同一ミリ秒に同じサイズで
  書き換えられた場合だけ取りこぼすが、archive は移動後に書き換えない運用なので受容する。
- `readFrontmatterData` は部分読みでも全文読みと同じ結果になることをテストで担保している
  (任意の読み取り長で `parseFrontmatter` の結果と一致することを総当たりで検証)。
  CRLF のファイルで読み取り境界が `\r` と `\n` の間に落ちると誤判定する穴があり、
  末尾が裸の `\r` なら全文へフォールバックすることで塞いだ。
