## 判断内容

タスクファイル(`.agent/tasks/<ID>.md`)の衝突を機械的に解消する際、ブランチ側を採用する挙動は
そのまま維持し、破棄する main 側の差分を**常に**マージコミットのメッセージ本文へ記録する。
「main 側の変更が ccloop の機械記録か人間の手編集か」の判別は行わない。

## 理由

判別手段として著者情報を使う案を検討したが、成立しない。ccloop が失敗記録などを書き込む
コミットも、リポジトリの git 設定(人間の `user.name` / `user.email`)の著者で作られるため、
機械記録と人間の編集は著者では区別できない。

コミットメッセージのパターン照合で判別する案もあるが、ccloop 側のメッセージ文言を変えるたびに
壊れる脆い結合になる。判別を誤って人間の編集を「機械記録」と分類すると、まさに直そうとしている
「黙って捨てる」状態に戻る。

判別せず常に残す場合のコストは、機械記録が捨てられる通常ケースでコミットメッセージが数行伸びる
ことだけである。誤判別のリスクと引き換えに払う代償として妥当と判断した。

## 検討した代替案

- **著者で見分ける**: 上記のとおり区別できないため不採用。
- **`ccloop status` の要対応に出す**: 人間の目に触れやすいが、実行時状態への書き込みが必要で
  変更範囲が広い。マージコミットのメッセージは `git log` で恒久的に追え、破棄の事実と内容が
  同じ場所に残るため、まず低コストな側を採った。効果が不足するようなら後から追加できる。
- **ブランチ側採用をやめて衝突を人間に回す**: 通常ケース(機械記録との衝突)まで手作業に
  落ちるため不採用。タスクの完了条件でも既存方針の維持が指定されている。

## 影響範囲

`lib/merge.ts` の `resolveMechanically` / `mergeCommitMessage` と、新規の `discardedOursDiff`。
差分は 60 行を上限に切り詰め、超過分は省略の注記に置き換える(コミットメッセージが
際限なく肥大化しないため)。差分の取得に失敗した場合は記録を諦めてマージを続行する
(記録のためにマージを止めない)。
