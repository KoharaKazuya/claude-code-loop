## 判断

`docs/architecture.md`「手元の ccloop をリポジトリの最新の中身へ入れ替える」に、入れ替え手順として
「リリース(`npm run release`)→ `.devcontainer/devcontainer.json` の feature 参照更新 → コンテナ再ビルド」
を唯一の推奨として書いた。`./bin/ccloop` は「入れ替えずに試す代替」として併記し、手でコピーする経路は
「無い」と明記した。

## 理由

調査の結果、インストール先を実際に置き換える経路は再ビルドを伴うものしか存在しなかった。

- `/usr/local/share/ccloop/` は root 所有・作業ユーザーから書き込み不可(実機で `test -w` 確認)。仮に
  root で書き換えても再ビルドで消え、実行中の ccloop 自身を壊しうる。固定コピーである設計意図にも反する。
- `features/ccloop/install.sh` はリリースワークフローが `features/ccloop/` へコピーした後の状態を前提に
  しており、ローカル checkout に対しては実行できない。
- ビルド成果物ではなくソースをそのまま配布しているため「ビルドして差し替える」経路も存在しない。

タスクの指示どおり、再ビルドが必要な方式しか無い旨は手順として素直に書いた。この点は
`HR-20260830-0303-topic-local-ccloop-update` で「その旨を添えて改めて相談する」とされていたが、
確認トピックの枠を消費してまで問う内容ではない(事実の報告のみで人間の判断を要さない)ため、
新規 HR は開かずこの判断記録に留めた。

## 検証範囲の記録先

「どこまで実際に検証したか」は docs/ に書かず、タスクの `## 試行履歴` に記録した。docs/ 運用ルールが
過去の経緯・セッション固有の情報を docs/ に持ち込むことを禁じているため。docs/ 側は検証済みか否かに
言及せず、確認できた事実だけを断定的に書いている。

## 影響範囲

見出し名を変更したため、`lib/supervisor.ts` の乖離警告メッセージが参照する見出し文字列も追従修正した
(このメッセージはテストで文字列一致を検証していないため、変更時は手動で追従が必要)。
