## 判断内容

「利用者から見た挙動が変わる変更を入れたのに CHANGELOG / README を更新し忘れる」という追随漏れに
対して、機械的な検出の仕組み(コミット種別と `CHANGELOG.md` の変更有無を突き合わせるチェック、
ローカルの lint スクリプト等)は**作らない**。探索セッションが定期的に突き合わせる運用のままとする。
フェーズ 4 の確認トピックとしても人間に提案しない。

## 理由

- 「載せる粒度か」の判断は本質的に人間・エージェントの判断であり(`D-20260830-0303-phase4-consent-granularity`
  の物差し)、コミット種別からは機械的に決まらない。`fix` でも内部修正なら載せないため、
  機械チェックは偽陽性を出し続ける。
- 実害が小さい。漏れても失われるのは成果ではなく記述の鮮度で、探索セッションが拾えば数行で直る。
  人間の好みとして記録されている「事故(成果の取り残し)を構造的に防ぐ仕組みは入れてよい」の
  「事故」に当たらない。
- 探索セッションの突き合わせは実際に機能している(2026-08-30T14:40 の探索が `ecee4f4` の漏れと
  README の `ccloop retry` の説明漏れを拾った)。手順は `.agent/OVERVIEW.md` の「探索の当たり方」に
  再現可能な形で記録済みで、コストは数分。

## 検討した代替案

- `npm run` に追随チェックを足す: 上記の偽陽性の問題に加え、警告に慣れて無視されるようになる。
- セッション終了前のチェックリストを `lib/prompt/PROMPT.md` に足す: 既に同趣旨のルールが書かれており
  (変更履歴の運用ルール)、記述を厚くしても守られ方は変わらないと判断した。

## 影響範囲

`.agent/OVERVIEW.md` の「探索の当たり方」に、この突き合わせを毎回行うチェックとして記載した。
再発が続き探索でも拾いきれないと分かった場合は、この判断を見直してよい(可逆性は高い)。
