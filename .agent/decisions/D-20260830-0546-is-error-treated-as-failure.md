## 判断内容

`finishTaskSession` の結果分類に、終了コード 0 でも結果 JSON が `is_error: true` を立てている
セッションを失敗として扱う分岐を追加した。ターン数上限(`subtype: error_max_turns` /
`terminal_reason: max_turns`)は専用の失敗種別 `max-turns` に、それ以外の `is_error: true` は
既存の `crash` に振る。挿入位置は `exitCode !== 0` の直後・`!taskFileChanged && statusUnchanged`
(最後の安全網)の直前。

## 理由

- ターン上限だけを特別扱いすると、`exitCode 0` + `is_error: true` になる他の終了理由
  (`error_during_execution` など)が同じ穴に落ちる。既定を「`is_error: true` は失敗」にした。
- 種別を分けたのは試行履歴の助言文を出し分けるため。ターン上限には「範囲が大きすぎる可能性が
  あるので分割を検討」という固有の助言が要る。

## レートリミットとの関係(確認したこと)

`recordMetrics` 周辺のコメントが「成功扱いの is_error: true」に言及しているのはレートリミット
到達セッションのことである。この前提は今も有効で、レートリミットは失敗として数えない
(`retries` を増やさない)設計のままにする必要がある。

安全性は二重に担保されている。

1. 分類チェーン上、レートリミット判定(`rateLimited`)は今回の分岐より前にあり、
   該当すればそこで分岐が確定する。
2. `detectRateLimit`(`lib/ratelimit.ts:12`)は `exitCode === 0` なら常に false を返す。
   つまりレートリミットとして検出されるセッションは終了コードが 0 ではなく、
   その手前の `exitCode !== 0` 分岐で確定するため、今回の分岐には到達しない。

## 検討した代替案

- **ターン上限だけを失敗にする**: 穴が残るため採用しなかった。
- **マージ衝突系より前に置く**: 採用しなかった。衝突は worktree を残して次回に衝突解消
  セッションを起こす特別なフローであり、そちらを優先しないとフローが壊れる。
- **最後の安全網より後ろに置く**: 採用しなかった。ターン上限のセッションはタスクファイルに
  書き込んでいることが多く安全網をすり抜けるうえ、記録される理由も具体性を失う。

## 影響範囲

ターン上限・エラー終了のタスクセッションが `retries` を消費するようになり、`maxRetries` に
達すれば `failed` になって人間の目に触れる。これまで無限に再選択されていたタスクが止まる。
`HR-20260830-0429-topic-oversized-task-timeout`(時間切れが 3 回続くタスクの扱いをどうするか)
の議論対象に、ターン上限で 3 回失敗するタスクも含まれることになる。
