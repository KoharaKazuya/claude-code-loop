## 判断内容

`lib/settings.template.json` の `permissions.deny` と `lib/prompt/PROMPT.md`「Bash 実行の権限制約」節の
deny 説明の一致を、`lib/deny-consistency.test.ts` で次の粒度で検査する。

- PROMPT.md 側は「節 → deny 箇条書きブロック → その中の inline code span 集合」を機械的に抽出する。
- テンプレートの deny パターン → PROMPT.md に現れるべき inline code トークンの対応表
  (`EXPECTED_MENTIONS`)を持ち、双方向に検査する。
  - 表に無いテンプレートエントリがあれば落ちる(素通りさせない)
  - テンプレートに無い表のキーがあれば落ちる(表自体の陳腐化を防ぐ)
  - 表の期待トークンが PROMPT.md に無ければ落ちる(deny 追加時の書き忘れ検知)
  - PROMPT.md 側に表由来でない inline code があれば落ちる(逆方向の検知)

## 理由

- 文字列の完全一致は課さない。PROMPT.md はセッションに読ませる散文であり、`Bash(git push*)` のような
  パターン文字列をそのまま列挙してはいない。完全一致を強いると PROMPT.md の可読性を犠牲にするか、
  将来の編集者がテストを緩める方向へ倒れる。
- 一方で「言及があればよい」だけでは緩すぎるため、対応表で「このパターンならこの語」を固定し、
  表の両方向の網羅性もテストで縛る。表は陳腐化しうるので、表自体を検査対象に含めるのが要点。
- inline code span を突き合わせ単位にしたのは、散文中の識別子が慣習的にバッククォートで囲まれており、
  機械抽出が安定するため。逆方向の検査もこの単位でしか成立しない。

## 検討した代替案

- deny パターン文字列を PROMPT.md にそのまま列挙して完全一致させる: 上記のとおり可読性を損なうため不採用。
- 対応表を持たず「deny のコマンド名が節のどこかに出現すること」だけを見る: `merge` `reset` のような
  一般語が別の文脈で出現しても通ってしまい、逆方向の検知もできないため不採用。

## 影響範囲・補足

- `lib/settings.ts` が実行時に追加する state ディレクトリ配下への Edit deny(自己改変禁止)は、パスが
  リポジトリごとに変わるためテンプレートに書けない。PROMPT.md ではこれを inline code なしの散文で
  説明しているため、現状の逆方向検査には引っかからない。将来 inline code で言及する場合に備えて
  `TEMPLATE_FREE_MENTIONS` という明示的な許容リストを空で用意してある。
- allow リストの一致は検査対象に含めていない。GOAL の制約が deny を対象としており、allow のズレは
  「classifier を通るので遅い」程度の影響にとどまるため。
- 検査ロジック自体が機能していること(ズレたときに実際に落ちること)は、純粋関数へ切り出したうえで
  合成入力による自己テストで担保している。
