## 判断内容

タスク T-20260830-0810 の作業項目「現時点で未掲載の決定を index.md へ追記して解消する」を、
このブランチでは**実施しない**ことにした。ブランチ側の `.agent/decisions/index.md` は
マージ基点(65f7080)の内容へ戻し、main 側の版がそのまま残るようにした。
未掲載分の解消は、同じタスクで一本化したリコンサイル(`lib/rotate.ts` の `rotateDecisions()`)に委ねる。

## 理由

このセッションの開始時刻(10:07)に、main 側で人間が index.md のチェックボックスを 8 件
`[x]` へ変更したコミット(118090a、`Agent-Auto: supervisor-state`)が入っていた。
一方ブランチ側の index.md は、その人間の操作より前(09:52)にリコンサイル結果で作り直した版である。

- ブランチ側の版を main へ持ち込むと、**人間が付けたばかりのチェック 8 件を消す**ことになる。
  チェックは人間にしか付けられない入力であり、機械的に作り直した一覧で上書きしてよいものではない。
- 加えて、両側が index.md の同じ領域を書き換えているためマージは再び衝突する。稼働中の公開版
  0.4.1 の `lib/merge.ts` には index.md の 3-way マージ(`mergeDecisionsIndexText`)が無く
  (`grep decisionsIndex` が 0 件、解決対象は `ownTaskFile` のみ)、衝突は機械的に解決されず
  人間判断へ回る。前回の試行が失敗したのもこれが原因である。同じ衝突を繰り返せば、
  このタスクの本体である `lib/` の修正がいつまでも main へ入らない。
- ブランチ側の index.md を基点の内容に戻せば、その差分は「ブランチは変更していない」状態になり、
  main 側の版がそのまま採用されて衝突が起きない。失う情報は無い(未掲載分はリコンサイルが
  次に走ったときに ID 降順の正しい位置へ自動で追加される。これがこのタスクで確立した仕組みそのもの)。

## 検討した代替案

- **main の版に未掲載分を足した版をブランチへ置く**: 人間のチェックは守れるが、両側の差分が同じ領域で
  交錯するため衝突は避けられない。0.4.1 が機械的に解決できない以上、本体の修正が止まる。採らない。
- **ブランチ側の版を優先する**: 人間のチェック 8 件を消す。採らない。

## 影響範囲

- 未掲載の決定(このブランチが増やした D-20260830-0947 / D-20260830-1018 を含む)は、
  次のリリース以降のリコンサイルが走るまで index.md に載らない。公開版 0.4.1 が動いている間は
  決定が件数基準でアーカイブされ続ける点も変わらない(`.agent/archive/decisions/` に残るので失われはしない)。
- タスクの完了条件「セッションの注意力に頼らず防がれていること」は `lib/rotate.ts` 側で満たしており、
  この判断はそれを取り消さない。
