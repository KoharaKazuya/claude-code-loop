## 判断内容

未コミット差分のパッチ退避に失敗したとき、worktree とブランチを削除せず残す。残したことは
state ディレクトリの `salvage-failures/<taskId>.json` に記録し、`ccloop status` の「要対応」に出す。

## 理由

退避の失敗を `null`(差分無し)と区別できていなかったため、失敗しても削除が続行され、
git 履歴にもパッチにも残らない差分が復元不能に失われていた。削除を止めるのが本質的な安全網であり、
退避処理そのものを頑健にする(バッファ上限の除去)のはその手前の対策にすぎない。

## 検討した代替案

status の既存項目(衝突 worktree・退避ブランチ)はすべて git へのライブクエリだけで組み立てており、
それに倣って「タスクが実行中でなく、衝突も無いのに残っている worktree」を退避失敗とみなす案も
あった。採らなかったのは、失敗の時刻とエラー内容を人間に見せられないため。原因が分からないと
人間は差分を回収してよいのか判断できない。

マーカーは `loadSalvageFailures` が読むたびに、worktree が既に消えているエントリをファイルごと
削除する(自己清掃)。人間が片付ければ status から自然に消えるので、掃除のためのコマンドを
増やさずに済む。表示経路が副作用を持つのは通常なら避けるところだが、溜め込まないことを優先した。

## 影響範囲

`salvagePatch` を呼ぶ 3 経路(起動時復旧・worktree の退避・通常の終了処理)すべて。
退避に失敗した worktree はブランチごと残るため、同じタスクの次の試行はその worktree を再利用する。
