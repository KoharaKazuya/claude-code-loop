## 判断内容

セッション終了時の結果分類(`finishTaskSession` の「6. 結果の分類」)の順序を
「利用上限 → タイムアウト → それ以外」に変えた。あわせて、利用上限の判定対象を
セッションの終わり方で分けた。

- タイムアウトで kill されたセッション: **stderr のみ**を文言判定の対象にする
- それ以外: 従来どおり stdout + stderr

## 理由(この線引きにした根拠)

順序を変えるだけだと、判定対象が広すぎて本物のタイムアウトを利用上限と誤認する余地が残る。
誤認は「retries を消費しない」= 失敗が確定しない、を意味するので、
「タイムアウトは 3 回で failed になる」安全網を壊しうる。そこで根拠となる出力を絞った。

絞る境目を stdout / stderr に置いたのは、セッションを `--output-format json` で起動しているため。
CLI は結果 JSON を実行の最後にまとめて stdout へ出すので、タイムアウトで kill されたセッションは
**結果 JSON を出す前に殺される**。つまりタイムアウトしたセッションの stdout に上限らしき文言が
載っていたとしても、それは CLI が「上限に当たった」と報告したものではない。
一方、CLI が実行中に出す通知は stderr に出る。

したがってタイムアウト時に stdout を無視しても、拾いたい証拠(CLI 由来の上限通知)は落ちず、
落ちるのはノイズだけになる。逆に非タイムアウト時は結果 JSON が stdout に出るため、
従来どおり両方を見る必要がある。

## 検討した代替案

- **順序だけ入れ替える(判定対象は stdout + stderr のまま)**: 実装は最小だが、上記のとおり
  本物のタイムアウトを取り違える余地が残り、安全網の担保が「文言正規表現の精度」だけになる。
- **タイムアウト × 利用上限が連続した回数に上限を設け、超えたら本物のタイムアウトとして数える**:
  誤検出時の無限ループを機械的に止められるが、新しい永続状態(連続回数)が要る。
  判定対象を絞れば誤検出の確率自体が十分低いため、状態を増やすほどの利得はないと判断した。
  誤検出が起きても実害は「backoff の待機が 1 回入る」だけで、失敗の取りこぼしは
  次のセッションで再評価される。

## 影響範囲

- `nextFastCrashStreak` は挙動を変えていない。タイムアウトを先に見て streak を 0 に戻すのは、
  数十分走ったセッションはいずれにせよ「瞬時クラッシュ」ではないため。分類順とは独立に正しい。
- 探索セッション(`runExploreSession`)は元から利用上限をタイムアウトより先に見ており、
  判定関数を共有しているので、この変更で両経路の扱いが揃った。
- 利用上限と判定されたセッションは `fail()` を通らないため失敗記録・worktree の park を行わない。
  これはタイムアウトでない利用上限で元からそうなっていた挙動を、タイムアウトの場合へ広げたもの。
