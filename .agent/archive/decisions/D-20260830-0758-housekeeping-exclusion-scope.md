## 判断内容

記録の片付け(`.agent/archive/` へのローテーション + 退避パッチの掃除)の契機を 2 つにした。

1. 走行中セッションが 0 の周回(従来どおり)
2. 探索セッションの起動直前(今回追加)

2 は走行中のタスクセッションと並走しうるため対象を絞る。絞るのは
**走行中タスクセッションが担当しているタスクのタスクファイルだけ**で、decisions と human-review には
除外を適用しない。

## 理由(この線引きで安全な根拠)

- タスクファイル: 走行中セッションは担当タスクファイルを自分のブランチで必ず書き換える(status 更新・
  `## 試行履歴` の追記)。main 側で先に archive へ移動すると、後の自動マージが modify/delete の
  衝突になる。ゆえに除外する。
- human-review / decisions の個別ファイル: 走行中セッションがこれらに行うのは新規作成のみで、
  片付けの対象になる「終わったもの」(closed な Review・`[x]` が付いた判断)を書き換える経路が無い。
  移動しても衝突しない。
- `decisions/index.md`: 並走する 2 セッションが同じ領域を触りうる唯一のファイルだが、
  ID 突き合わせの 3-way マージで機械的に解決される既存経路がある(`lib/merge.ts`)。
  modify/delete のような致命的衝突にはならない。
- 探索セッションの起動直前は mainLoop の同期区間で、マージ・自動コミットが走らない。

起動「直前」を選んだのは、探索セッション自身が整理後の記録を読めるため(片付けの目的である
読み取りコストの削減がその場で効く)。

## 検討した代替案

- 一定時間ごとに走行中でも安全な範囲だけ片付ける: 人間の回答(`HR-20260830-0429-topic-housekeeping-while-busy`)で
  採らないと決まった。細かくしすぎない方針。
- 走行中セッションが触るファイルを一つひとつ除外する: 同じ回答で明示的に避けるよう指示された。
  複雑な線引きは持ち込まない。

## 影響範囲

`rotate()` に `excludeTaskIds` オプションが増えた。契機が増えたことで、タスクが途切れない状況でも
記録が溜まり続けなくなる。
