## エージェント運用ルール

- この節はメインセッション(指揮役)にのみ適用する。自分がサブエージェント(Task ツールで起動された側)である場合はこの節を適用せず、さらなる委譲はせずに与えられたタスクを自分で完結する(委譲指示で明示的に再委譲を許可された場合を除く)。
- メインセッションは指揮役。設計、タスク分解、結果の統合、レビューに専念し、調査・実装・検証は Task ツールで委譲する。難所や設計判断が密な作業のみ直接扱ってよい。
- 着手前に「委譲するか、直接扱うか」を宣言してから作業する。直接扱えるのは難所に限り、なぜ難所かを一言添える。宣言なしに Edit/Write で実装を始めない。
- 「設計が固まってから委譲する」を直接作業の言い訳にしない。設計に必要な調査も委譲して要約で受け取り、メインが直接読むのは委譲指示を書くのに必要な最小限にとどめる。設計が固まった後の実装は機械的な作業であり、委譲する。
- モデルの明示は必須。通常は `model: sonnet`、難所(複雑な設計判断、大規模リファクタ、難解なバグ)は `model: opus`。未指定はメインのモデルを継承し高コストになるため、省略しない。
- 指示は自己完結させる。ファイルパス、目的、制約、完了条件を渡し、範囲外の変更とユーザー変更の上書きを禁じ、競合の可能性があれば停止して報告させる。
- 結果は構造化した要約で受け取る。メインのコンテキストでファイルを大量に読まない。
- メインの読み込みは最小限にする。Grep で該当箇所を特定してから Read の offset/limit で部分読みし、大きいファイルの全文 Read や `cat`/`head` による複数ファイルの連結読みはしない(結果が以降全ターンの履歴に載り続け、コンテキストを恒久的に膨らませる)。まとまった読み込みが必要ならサブエージェントに読ませて要約で受け取る。
- 検証方法は変更内容とリポジトリの実態に応じて選ぶ。未検証事項は推測で埋めず明示させ、メインが確認する。
- 実装完了後のレビューは reviewer サブエージェント(`.claude/agents/reviewer.md` は `lib/agents/reviewer.md` への
  シンボリックリンク)で行う。

## docs/ 運用ルール

docs/ は今後のエージェント・人間が作業時に参照するための情報置き場として整理・維持する。

- 常に「最新の信頼できる情報」が書かれた状態を維持する。「これまで○○だったが変更した」のような過去の知識を前提とする書き方や、`.agent/` 以下の情報・タスク情報と結びつけた書き方は避ける。過去の経緯は `.agent/` や Git 履歴から読み取れるため docs/ には書かない。
- コードを読むだけでは読み取りづらい抽象的な情報、背景、理由(なぜこの設計・方針なのか)を中心に記載する。コードから自明な事実の羅列は書かない。
- README.md からたどり着けるようにする(README にリンクを置く)。
- 量を増やしすぎない。かならず読まれるわけではない前提で、読者(エージェント・人間)が得たい情報にたどり着けること、たどり着いた場合に効果がある内容だけを残すことを重視する。
- このリポジトリを触る開発者に伝えて意義がある内容かどうかを掲載基準にする。
- セッション中に発見した重要な事実(コードから読み取りづらい制約、外部仕様の挙動、設計の背景・理由、ハマりどころ等)は、そのセッションのうちに docs/ 以下の適切な箇所へ反映する。「後で書く」を残さない。判断の経緯は `.agent/decisions/` に書き、一過性の情報は記録しない(掲載基準は上記に従う)。
- タスク単位の試行知見(失敗の経緯・次の試行への申し送り)は docs/ に書かず、該当タスクファイル本文末尾の `## 試行履歴` セクションへ書く(書式は `lib/prompt/PROMPT.md`)。

## 変更履歴(CHANGELOG.md)の運用ルール

`CHANGELOG.md` は利用者向けのリリースノートである。古くならないよう、変更を入れたセッションがその場で更新する(後続のセッションやリリース作業に持ち越さない)。

- 利用者から見た挙動が変わる変更を入れたら、その変更と同じコミットで「## 未リリース」節に 1 行足す。
- 載せる/載せないは「利用者向けリリースノートに 1 行として載る粒度か」で判断する。これはフェーズ 4 の個別確認と共通の物差しであり、二重に基準を作らないこと。新機能・サブコマンド・表示項目の追加、既定値や出力の変更、破壊的変更、利用者が踏んでいた不具合の修正は載せる。内部の作り替え、テストの追加、docs/ の記述改善、`.agent/` の記録は載せない。
- 物差しは共通だが、「着手前に確認を取るか」と「変更履歴に載せるか」は同じ集合ではない。不具合の修正は、壊れているものを直すのに同意を求める意味がないため確認は取らないが、変更履歴には載せる。
- 利用者の言葉で「何ができるようになったか・何が直ったか」を書く。内部の関数名・ファイルパス・タスク ID・バージョン番号以外の内部事情は書かない。
- リリース時に「## 未リリース」節を「## <バージョン> — <日付>」見出しへ繰り上げるのはリリーススクリプト(`npm run release`)が自動で行う。手でバージョン見出しを作らない。
- 同趣旨のルールは `lib/prompt/PROMPT.md`(自律セッションへ注入される共通ルール)にもある。片方だけ変更しない。

## コミット運用ルール

- コミットメッセージは日本語で記述する。
- 意味ある一塊の単位で、随時自律的にコミットする。ユーザーの指示を待たない。
- 以下の worktree 運用は対話セッション(人間が直接起動したセッション)にのみ適用する。`ccloop run` 起動セッションは既に専用 worktree 内で動いているため適用せず、「自律実行モード」節と `lib/prompt/PROMPT.md` に従う(worktree の追加作成・ブランチ操作・main へのマージはしない)。
  - 変更作業は基本的に git worktree 上で行う(EnterWorktree ツールを基本手段とする)。main ワーキングツリー上で直接編集・コミットしない。
  - ブランチ名に `agent/` プレフィックスは使わない(Supervisor が管理する名前空間のため)。
  - 作業が完了し機械的検証(tests / lint / typecheck のうち該当するもの)が通ったら、セッション自身が main へ `git merge --no-ff` で統合し、worktree とブランチを片付ける。コンフリクトした場合は解消してから統合する。
  - 例外: 軽微な変更(typo 修正、ドキュメントの小さな修正など、検証不要で 1 コミットで終わるもの)は main へ直接コミットしてよい。

## 自律実行モード(`ccloop run` 起動セッション)

`ccloop run` から起動されたセッションには `lib/prompt/PROMPT.md` が system prompt として注入され、
そこに書かれた共通ルール(worktree・自動マージ・絶対ルール・Bash 実行の権限制約など)に従う。
本ファイルの worktree 運用(EnterWorktree・main への自律マージ)はそのセッションには適用しない。

## Bash 実行の権限制約

`ccloop run` 起動セッションの Bash 権限は `lib/settings.template.json` の既定 permissions に従う。
`.agent/claude-settings.json` があれば、そこに追記された allow/deny がツール既定に対する
上書き差分として適用される(deny が allow に優先)。制約の詳細(permission mode・deny 一覧・allow の
役割など)は `lib/prompt/PROMPT.md` の「Bash 実行の権限制約」節を参照する。
